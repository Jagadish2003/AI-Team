# Audit completeness — what is covered, and what is not (2.0-D4 T1, AC1)

The trail's coverage, stated as a number rather than a claim, plus the reasoning
behind every route that deliberately does not audit.

Source of truth: `backend/app/middleware/audit.py` (the write point and the
registry) and `backend/tests/contract/test_audit_conformance.py` (the sweep that
enforces this document in CI).

---

## 1. Current coverage

| | Count |
|---|---|
| State-changing route keys on the live app | **56** |
| Audited | **37** |
| Declared exempt (legitimately no audit) | **5** |
| Declared gaps (a real hole, with an owner) | **14** |
| **Undeclared** | **0** |

Keyed on **method + path**, not path. `POST /api/stack-builder/setup-state/{org_id}`
audits and `DELETE` on the same path does not; path-keying let the POST's coverage
mask the DELETE's gap.

## 2. The actions D4 names by hand

D4 enumerates the actions it expects audited. Each is mapped to its routes and
checked in CI by `TestD4NamedActions::test_every_named_action_with_a_route_audits`.

| D4-named action | Status | Event type |
|---|---|---|
| Connector create | audited | `connector_connected` |
| Connector edit | audited | `connector_configured` |
| Connector delete | audited | `connector_disconnected` |
| Scope pin/unpin | audited (8 routes) | `scope_declared` |
| Run start | audited (2 routes) | `run_started` |
| License install | audited | `license_installed` |
| Export generation | audited | `audit_export_generated` |
| Learning adjustment/reset | audited | `ranking_adjustment_changed` |
| Analyst decisions | audited (3 routes) | `opportunity_decision_recorded`, `evidence_decision_recorded`, `opportunity_feedback_recorded` |
| Pack activate/disable/rollback | **no route yet** — 2.0-C1 | — |
| Entity merge/unmerge | **no route yet** — 2.0-B2 | — |

The last two are recorded in `ACTIONS_PENDING_ROUTES` so the sweep cannot pass
vacuously by looking for a route nobody has built, and
`test_pack_and_entity_actions_have_no_route_yet` fails the moment those routes
appear.

## 3. Why "the event type is registered" was not enough

The check that existed asserted each named action's event type was in
`AUDIT_EVENT_REGISTRY`. `SCOPE_DECLARED` was registered and the check passed —
while **all seven SaaS scope routes wrote nothing at all**. The cloud connector
and native-DB scope paths emitted the type, so the constant existed, and a
registry-level assertion cannot tell the difference.

That is why the assertion is now about **routes**, not constants. It is the
difference between "this vocabulary exists" and "this action is recorded".

A second, related distinction the suite keeps separate:

* `test_audit_conformance.py` proves a route **can reach** `log_event`, by
  walking the call graph.
* `test_d4_named_action_audit_records.py` drives the route and **reads the stored
  row back**, checking actor, org, target, timestamp and outcome.

"The handler calls `log_event`" and "an audit record exists" are different
claims, and only the second is what a reviewer asks for.

## 4. Scope pin/unpin

The largest hole, and the one with the clearest security reading: a scope
selection decides what AgentIQ is allowed to read for an org, for **every future
run**. Widening it is a data-access grant.

All seven SaaS routes emit through **one** helper
(`app/connector_scope_audit.py`) rather than seven copies — seven copies drift the
moment one route changes, which this repo has already been bitten by elsewhere,
and one helper keeps the payload comparable across connectors.

Two payload decisions worth keeping:

**Pinned and unpinned are recorded, not just the result.** A row carrying only
the new selection forces a reviewer to diff consecutive rows, and cannot answer
the question at all for the first write. "Who added the #finance channel?" needs
the delta.

**`first_selection` is flagged.** Before a selection is saved, most connectors
read everything they can see. So the first save is usually a *narrowing* even
though every id shows as pinned — without the flag, that row reads as a broad
grant when it was the opposite.

## 5. The two bypass registries

Deliberately spelled differently, because they are different claims.

**`AUDIT_EXEMPT_ROUTES` (5)** — legitimately no audit, with a reason. Read-shaped
POSTs (`/connectors/{id}/test`, `/audit/export/verify`), authentication
(`login`/`logout`, recorded by the auth layer's own `login_attempts` table), and
`forgot-password` — which is deliberately unaudited at request time because it is
reachable by anyone with an email address, so auditing it would let an outsider
write rows into a customer's trail.

**`KNOWN_AUDIT_GAPS` (14)** — a real hole, with a reason and an owner. None is an
action D4 names. They fall into:

* auth / membership lifecycle (register, invite, accept-invite, password change
  and reset, org approval/rejection, member add) — the credential-change ones are
  what a security review will ask about next;
* run lifecycle (`compute`, `replay`, setup-state delete);
* analyst / lifecycle (`opportunity-lifecycle/track`);
* data in (`uploads`).

The gap list is a **ratchet**: a route missing from it fails the sweep, and a
declared route that has *since gained* audit also fails. It can only shrink.

## 6. Proven to reject

A sweep that has never been observed failing is not known to be a sweep. Verified
by experiment:

| Sabotage | Result |
|---|---|
| Add an unaudited mutating route | sweep red |
| Remove an existing emission | sweep red |
| Delete a gap declaration | sweep red |
| Emit an unregistered type | `log_event` raises |
| Strip the scope-audit call from one route | 4 record tests + 3 sweep tests red |
| Strip the configure audit | 2 record tests + sweep red |
| Choose the event type by a conditional expression | registry-governance test red |

The last one is not a hypothetical — the first draft of the connect route used
`CONNECTOR_CONNECTED if now_connected else CONNECTOR_DISCONNECTED`, and the sweep
correctly refused to verify a type it could not resolve statically. It is now two
explicit calls.

---

## 7. A write failure still does not fail the action

Unchanged, and the reasoning is in `audit.py`'s docstring because a federal
reviewer will ask: the state change is already committed (refusing the response
would report a failure that did not happen), the failure is not silent
(`audit.write_failed` telemetry), and making the audit write a prerequisite would
turn an audit outage into a total outage.

An **unregistered event type** is treated differently and raises — it is a
deterministic programming error that request data cannot cause, not an
operational condition.

---

## 8. Adding a state-changing route

1. Emit `log_event` with a **literal** registered constant, carrying `target` and
   `outcome`.
2. If the type is new, add and register it in `audit.py` **before** the first
   emission site.
3. Never copy request values into the payload — record *which* settings changed,
   not their contents.
4. If it genuinely should not audit, declare it in `AUDIT_EXEMPT_ROUTES` with a
   reason. If it should but does not yet, declare it in `KNOWN_AUDIT_GAPS` with a
   reason **and an owner**.

Doing none of these fails the build, which is the point.
