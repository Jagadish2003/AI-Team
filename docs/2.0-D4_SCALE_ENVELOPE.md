# AgentIQ scale envelope (2.0-D4 T4)

The volumes this deployment supports, how well-founded each number is, and what
happens at the edge.

Companion to `docs/MSP-B8_VOLUME_VALIDATION.md`, which this document deliberately
mirrors in structure: a stated number, the measurement it came from, and an
explicit note of where the evidence stops.

Source of truth: `backend/app/scale_envelope.py`. Served live at
`GET /api/run-health/volume`.

---

## 1. The envelope

| Dimension | Stated limit | Basis | Enforced? | At the edge |
|---|---|---|---|---|
| Cloud events per run | **250,000** | **measured** | yes — `RunBudget` | defer and count |
| Documents per run | **~1,024** (256 MiB budget) | operationally justified | yes — `DocumentIngestor` | defer and count |
| Connected systems per deployment | *no engineering limit stated* | provisional | commercial only | refuse with reason |
| Findings per run | **5,000** (reporting threshold) | provisional | **no** — by design | report only |

**One of four rests on a reproducible measurement.** That is the single most
important line in this document. Stating four confident numbers when only one is
measured would be exactly the marketing figure this work exists to avoid, so the
API reports `measuredCount: 1` alongside the numbers themselves.

---

## 2. Where each number comes from

### Cloud events per run — 250,000 (measured)

Derived in `discovery/signals/ops_calibration.py` from the MSP-B8 month-scale
validation run recorded in `docs/MSP-B8_VOLUME_VALIDATION.md`: 30,225 events
measured over a month, `ceil(8 × month)` rounded up to 250,000. At the measured
1.474 ms/event that is roughly a six-minute worst-case ingest stage.

This module **imports** that constant rather than restating it. A second literal
would drift the moment someone recalibrated `B8_MEASUREMENTS`, and an envelope
that disagrees with the component enforcing it is worse than no envelope. A test
pins the two together.

### Documents per run — ~1,024 (operationally justified)

What is actually enforced is a **byte** budget: 256 MiB extracted per run, with a
25 MiB per-file cap (`DOCUMENT_EXTRACTION_BUDGET_BYTES` /
`DOCUMENT_MAX_FILE_BYTES`). The document *count* above is that budget divided by
an assumed 256 KiB average extracted size.

That average is an assumption, not a measurement — which is exactly why this
dimension is not marked `measured`. A wrong average makes the stated count wrong
without making the enforced byte budget wrong.

### Connected systems per deployment — no engineering limit (provisional)

There is a **commercial** limit — the licence payload's `limits.max_systems`,
enforced at connect time by `app/license_limits.py` — and it defaults to
unlimited on a valid licence that scopes none. There is no *engineering* limit,
because none has been measured.

This is a **declared gap**, served as such by the API. Closing it needs a run
against a deliberately large estate, which no environment currently has. Stating
a number without that run would be inventing one.

### Findings per run — 5,000, reporting only (provisional)

Roughly an order of magnitude above the largest run seen in development. The
reasoning: a run producing more than this has almost certainly hit a detector
defect or a duplicated estate rather than genuinely found that many problems.

**Nothing is enforced, deliberately.** See §4.

## 3. What happens at the edge

No dimension degrades by dropping work. Three modes, and "drop it" is not one:

**`defer_and_count`** — the work is postponed and the postponement is reported.
Events past the budget produce a `BudgetReport` carrying
`budget`/`processed`/`deferred`/`seen`/`breached`, the deferral window and the
per-source split; the checkpoint does not advance past deferred volume, so the
next run resumes exactly where this one stopped. Documents past the per-run
budget are skipped with reason `budget_exceeded` and do **not** advance their
checkpoint, so they are retried.

A subtlety worth keeping: a file skipped as `size_capped` **does** advance its
checkpoint, because that outcome is deterministic — it will be too large next run
too. Counting it as "deferred" would promise a retry that never helps. The volume
report therefore counts `budget_exceeded` as deferred and `size_capped` as
reported-but-settled.

**`refuse_with_reason`** — a connect attempt beyond the licensed system count is
refused up front with a plain-language reason. Nothing is half-connected.

**`report_only`** — see below.

---

## 4. Why findings-per-run enforces nothing

A finding is the product's output. Silently withholding one to satisfy a volume
target would mean a customer never learns a real problem exists — a far worse
failure than a long list.

So exceeding 5,000 findings is reported as a fact on the run's volume report, and
every finding is still served. The report says so in as many words: *"Every
finding is still served — this is a prompt to check for a detector defect or a
duplicated estate, not a truncation."*

If a hard cap is ever wanted, it must defer-and-count like the others, never
truncate. That constraint is recorded on the dimension as a declared gap so the
next person to touch it inherits the reasoning.

---

## 5. Volume is not time

The trap this document exists to name. The native cloud connectors bound a run
**three** ways, not one:

| Bound | Default | Why it exists |
|---|---|---|
| Event budget | 250,000 events | volume |
| Per-scope poll cap | 4 polls (`CLOUD_EVENT_MAX_POLLS_PER_SCOPE`) | request count |
| Wall-clock deadline | 180s (`CLOUD_EVENT_POLL_DEADLINE_SECONDS`) | time |

A throttled provider exhausts patience long before it exhausts a volume budget.
An envelope stated purely in volume is therefore **true on a fast estate and
false on a throttled one**, so every dimension records the conditions its number
holds under, and the volume report distinguishes "stopped because the budget ran
out" from "stopped because a poll bound was reached".

`test_scale_envelope_load.py::TestVolumeIsNotTime` seeds exactly that case: a run
with the budget barely touched that still stopped early. The report must say so,
or the envelope reads as met when the ingest was incomplete.

## 6. How it is tested

`backend/tests/unit/test_scale_envelope_load.py` — for each dimension, a test at
the stated limit that passes and a test past it that demonstrates loud
degradation. The second is the one that earns its keep: proving the system
survives its maximum tells a customer little; proving that at 120% of maximum the
run completes with an explicit deferral report tells them what failure looks like
before they meet it.

The load tests drive real volume through the real enforcing components
(`RunBudget`, `OpsEventStream`, `NoiseFloorPolicy`) rather than asserting against
mocks. Budgets are injected rather than using the shipped 250,000 — what is being
proven is behaviour at the edge, and a quarter of a million synthetic events
would prove the same thing far more slowly.

Both key guarantees are verified to **fail when violated**: removing the
early-stop reporting turns the throttled-source test red, and making the report
claim findings were deferred turns four tests red.

`backend/tests/contract/test_d4_scale_envelope.py` covers the served surface.

---

## 7. Where to see it

`GET /api/run-health/volume` (analyst+, org-scoped). Returns the envelope with
every basis label and declared gap intact, plus — when a run is named or the
latest is resolved — that run's observation against it, including deferrals,
suppressions and a plain-language headline.

Two things deliberately in one place: what the deployment supports, and what this
run actually did against it.

## 8. Recalibrating

* **Events per run**: edit `B8_MEASUREMENTS` in
  `discovery/signals/ops_calibration.py` and re-derive. Do not edit the number in
  `scale_envelope.py` — it does not exist there.
* **Documents per run**: the enforced budget is
  `DOCUMENT_EXTRACTION_BUDGET_BYTES`. If a corpus is ever measured, update
  `ASSUMED_BYTES_PER_DOCUMENT` and promote the basis to `measured` **with the
  measurement cited**.
* **Systems per deployment**: promote from a declared gap only after a run
  against a large estate, and record which run.
* **Findings per run**: `SOFT_FINDINGS_ENVELOPE`. Keep it a reporting threshold.

Bump `ENVELOPE_VERSION` on any change to a stated number or a basis.
