# Degradation under partial failure (2.0-D4 T5)

What the platform does when part of it is unavailable, and how a customer can
tell exactly what they did and did not get.

Source of truth: `backend/app/degradation.py` (the vocabulary and the report
shape) and `backend/app/run_completeness.py` (the readers and probes).

---

## 1. The question this answers

Not *"does the platform stay up?"* — it largely does — but *"when part of it is
unavailable, can the customer tell?"*

The failure this exists to prevent is not a crash. It is a run that completes,
produces findings, and looks entirely normal while silently missing a source. A
user who does not know their ServiceNow data was absent reads the findings as
complete, and every decision downstream inherits that error. In an evidence
platform that is the worst failure mode available, precisely because nothing
appears wrong.

So the acceptance bar is stated as a negative, because that is how it will be
judged:

> **After a seeded failure, there must be no surface on which the run appears
> complete.**

---

## 2. One vocabulary, not five

The platform already degrades well in places. The AWS connector tracks
per-account health and keeps other accounts running; ServiceNow distinguishes an
unactivated plugin from a transport error; the operational-app ingestors skip a
target with a missing credential without touching its cursor. Each of those grew
its own word for it:

| Source | Word it grew | Canonical |
|---|---|---|
| `discovery/ingest/aws_health.py` | `ok` / `partial` / `failed` | as-is |
| `discovery/ingest/aws_health.py` | `auth_failed` | `unavailable` |
| ServiceNow SecOps tables | `unavailable` | `unavailable` |
| `discovery/ingest/operational_config.py` | `credential_missing` | `unavailable` |
| run stages | `degraded` | `partial` |
| model gateway | `ok=False` (no status at all) | `unavailable` |
| retrieval store | raises (deliberately) | `unavailable` |

A run-health consumer previously had to special-case each one. The canonical set
is:

* **`ok`** — everything asked of it, it did.
* **`partial`** — it worked, but not for everything. A real but incomplete answer.
* **`unavailable`** — it produced nothing, for a reason that is not an error: a
  plugin is not activated, a credential is absent, a provider is not configured.
  Customer-actionable, and **not a bug**.
* **`failed`** — it was reachable, tried, and failed. Usually a bug or an outage.
* **`unknown`** — its health could not be established. Deliberately **not `ok`**.

**Converging loses nothing that matters.** Every component keeps its native word
in `nativeStatus` alongside the canonical one. `auth_failed` and
`credential_missing` both read as `unavailable` because a customer sees the same
thing — no data from that source, and a credential is why — while an engineer
can still tell which code path produced it.

The mapping is also the enforcement point for the next source: a new subsystem
cannot introduce a sixth vocabulary without adding its words here, which means
deciding what a customer should see.

## 3. Four fields, all mandatory

Every degradation reports what was **attempted**, what was **delivered**, what is
**missing**, and a named actionable **reason** — plus a **remedy**. These are not
optional, because a degradation report missing any of them cannot be acted on and
will be ignored, which returns the customer to exactly the position this work
exists to fix.

```json
{
  "kind": "connector",
  "component": "servicenow",
  "status": "failed",
  "nativeStatus": "error",
  "attempted": "Ingest servicenow for this run",
  "delivered": null,
  "missing": "No servicenow data contributed to this run's findings",
  "reason": "HTTP 401: Session expired or invalid",
  "remedy": "Check the servicenow connection on the Integration Hub, then re-run discovery. Findings from other sources remain valid."
}
```

## 4. The three AC6 scenarios

They fail in genuinely different ways, so each gets its own reader rather than
one generic check standing in for all three.

### Connector outage

The best-covered case already: the run record carries `succeeded` and
`ingestErrors`. What was missing was **the comparison against what was asked
for**. A run that requested Salesforce, ServiceNow and Jira and succeeded on two
is not a clean run with fewer sources — it is a partial run, and until now
nothing said so.

A source that errored but was never requested still counts. An error nobody asked
for is more surprising, not less.

### Model-mode unavailability

The subtlest of the three and the reason this subtask is not just a connector
fix. All three providers degrade to `ok=False` or an **empty embedding list**
rather than raising — correct for resilience, terrible for visibility.

The shipped default is the sharp edge: `MODEL_EMBEDDING_PROVIDER=hosted` has no
embeddings endpoint, so every `retrieval_chunks` row stays pending for ever and
every search matches nothing. The run completes. Every screen looks normal. The
findings simply cite no documents, and nobody can tell that from findings that
legitimately had none.

`validate_provider_config()` already logs a warning for exactly this. This work
promotes it from a startup log line — which nobody reads after week one — to a
run-visible fact.

### Storage pressure

Three sub-cases that degrade differently and are kept separate rather than
collapsed, because a dead primary stops everything while a dead retrieval store
only stops citations:

1. **Primary Postgres** unreachable → `failed`. Everything runs through it.
2. **pgvector retrieval store** unreachable → `unavailable`. Findings from
   structured sources are unaffected, and the report says so.
3. **Evidence store** unwritable → surfaces through the same reader.

When the primary is down, retrieval reports **`unknown`, not `ok`** — see below.

## 5. Never a healthy number from an unhealthy source

The one posture generalised from existing code. R18-B2's freshness metrics
deliberately **raise** on a read failure rather than returning zeros, because "0
stale chunks" would report perfect freshness at the exact moment the store is
down.

Generalised here:

* an unrecognised status maps to `unknown`, never `ok`;
* rolling up **nothing** is `unknown`, not `ok` — an empty health picture is not
  a clean bill of health;
* a component that could not be measured because a dependency is down reports
  `unknown` — so a dead primary database makes retrieval health *unknown*, not
  *fine*;
* a roll-up is as bad as its **worst** component, never as good as its best.

## 6. Where it surfaces

| Surface | Field |
|---|---|
| `GET /api/runs/{runId}/status` | `completeness` |
| `GET /api/runs/{runId}/executive-report` | `runCompleteness` + corrected `sourcesAnalyzed` |
| `GET /api/run-health/degradation` | `completeness` (probes the live environment) |

All four read from **one** `RunCompleteness`, including the headline sentence.
Surfaces do not compose their own wording — that is what stops one saying
"complete" while another says "partial".

The executive report gets the most attention because it is the artifact most
likely to reach someone who will never open a health panel. Two things happen
there:

1. `runCompleteness` is stamped on, with the headline stating in as many words
   that the findings are partial. Applied to the **stored** report as well as a
   freshly composed one, so a report materialised before this shipped still tells
   the truth about its run.
2. **`sourcesAnalyzed.totalConnected` is corrected.** It counted the sources the
   run was *configured* with, so a run whose ServiceNow died reported the same
   "connected" count as a clean one. It now counts what actually succeeded, and
   gains `sourcesRequested` and `sourcesFailed` so the shortfall is visible
   rather than inferable.

The run-scoped surfaces read **only the run record** (`include_environment=False`)
— the question there is what *that run* delivered, not what the environment looks
like now. `/api/run-health/degradation` probes live, because "can this deployment
embed content?" is a question about the present.

## 7. How it is tested

`backend/tests/unit/test_degradation_vocabulary.py` — the vocabulary, the
roll-up, the never-`ok`-when-unmeasured posture, and each of the three scenarios
against its reader.

`backend/tests/contract/test_d4_partial_run_visibility.py` — the negative bar
across every served surface. The load-bearing test asserts directly that a
partial run's executive report **differs** from a clean one's; if those two ever
read alike, this subtask is not finished regardless of how good the health
endpoint looks.

Three guards were verified to **fail when violated**, not merely asserted:

| Sabotage | Result |
|---|---|
| Stop stamping `runCompleteness` on the executive report | 6 contract tests red |
| Count configured sources instead of succeeded ones | 1 contract test red |
| Map an unrecognised status to `ok` instead of `unknown` | 1 unit test red |

A guard never observed failing is not known to be a guard.

---

## 8. Adding a source

1. Map its status words in `NATIVE_STATUS_MAP`. If none fit, the question to
   answer first is what a *customer* should see — not what the subsystem calls it.
2. If it can fail in a way the run record does not already capture, add a reader
   or probe in `run_completeness.py`.
3. Fill all four fields. A degradation with no remedy is not actionable, and the
   contract tests enforce this for every non-`ok` component.

Bump `DEGRADATION_SCHEMA_VERSION` on any change to the served shape.
