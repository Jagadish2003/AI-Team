# AgentIQ Claude Instructions

## Purpose

AgentIQ is a full-stack discovery and opportunity-analysis app. The backend ingests enterprise system signals, detects workflow/friction patterns, scores opportunities, materializes run-scoped artifacts, and serves contract-shaped API responses. The frontend is a Vite React app that guides users through integration setup, discovery runs, source intelligence, opportunity review, pilot roadmap, agent blueprint, and executive report views.

Keep this file short and actionable. Prefer reading the relevant code and contract files over relying on this file for every detail.

## First Rules

* Protect user work. Check `git status --short --branch` before edits and do not revert unrelated changes.
* Do not commit secrets, generated databases, local env files, token files, or server keys.
* Preserve API response shapes. `contracts/API_CONTRACT.md` and `contracts/CONTRACT_RULES.md` are the source of truth when frontend and backend disagree.
* Run-scoped endpoints must include `runId` in the URL. Do not add "latest run" fallbacks.
* Before editing shared behavior, inspect existing route/context/test patterns and make the smallest compatible change.
* After code changes, run the narrowest relevant tests first, then broader tests when the change affects contracts, shared API helpers, routing, or pipeline behavior.

## Tech Stack

* Backend: Python 3.11, FastAPI, Pydantic, PostgreSQL (psycopg2) with `{ id, payload }` JSON payload tables, pytest.
* Frontend: React 18, TypeScript, Vite, React Router, Tailwind, Vitest, Testing Library.
* Data/pipeline: offline fixtures by default, optional live Salesforce/ServiceNow/Jira/nCino ingestion, pack-aware detectors and LLM enrichment.
* Auth: bearer token via `DEV_JWT`; default local token is `dev-token-change-me`.

## Repository Map

### Backend — App

* `backend/app/main.py`: FastAPI app, CORS, core API routes, route registration. Check here first to confirm any route module is actually registered.
* `backend/app/routes_*.py`: feature route modules. Registered modules include stack builder, stack builder launch, run lifecycle, replay, normalization, enrichment, blueprint, workspace catalog, connector/product APIs, temporal, DB connectors, and connector auth.
* `backend/app/salesforce_product_packs.py`: 2.0-D1 T5 single source of truth for **which pack serves which Salesforce product** — the PACK-level half of the anchor-on-shipped rule. The R191-R1 guard resolves the domain-specific product ids (`salesforce_fsc`, `salesforce_sc`, …) through `IMPLEMENTATION_ALIASES`, where they map to `{salesforce}`; that answers the CONNECTOR question ("can we authenticate and read from this org?") but NOT the pack question ("do we read this product's objects and detect its patterns?"). Before 2.0-D1, `salesforce_fsc` was already a PRIMARY `system_of_record` for `financial_services` and CI was green while no FSC pack, detectors or ingest existed — the alias hid it. Each product now declares its pack with a `kind` of `DEDICATED` (its own domain pack: `salesforce_sc`→`service_cloud`, `salesforce_ncino`→`ncino`, `salesforce_pss`→`strs_benefits`, `salesforce_fsc`→`financial_services_cloud`) or `GENERIC` (deliberately served by `service_cloud` because no domain pack exists — `salesforce_rc`, and `salesforce_hc` whose pack is explicitly deferred to 2.0.1), each with a required `reason`. The rule the guard enforces (`test_r191_r1_ingestor_registry_enforcement.py::TestPackLevelCapabilityGate`) is: a domain-specific product presented as connectable must declare a pack here AND that pack must be registered — so an undeclared claim, or one naming a non-existent pack, fails. `pending_domain_pack()` records the still-generic products so the remaining gap is visible rather than implied. This is the BACKEND source of truth; the frontend's `CLOUD_PACK_REGISTRY` (`StackBuilderPage.tsx`) is what actually selects packs at launch and a contract test pins the two together — a registry entry honestly gated as FSC-capable while the frontend selected `service_cloud` would be the same dishonesty relocated (2.0-D1 T5 fixed exactly that: `salesforce_fsc` now selects `financial_services_cloud`, so declaring FSC activates the FSC pack instead of falling back to generic Service Cloud detection). The gate is **proven to fail**, not just asserted: removing the FSC pack registration turns it red (verified by experiment and pinned by `test_gate_goes_red_when_a_declared_pack_is_unregistered`), because a gate never observed failing is not known to be a gate.
* `backend/app/connector_roadmap.py`: R191-R1 T5 (AT-726) single source of truth for the **anchor-on-shipped** rule on the Integration Hub connector catalog. A catalog tile whose ingestion does not ship yet (SAP/`dynamics365` have an auth/config but no ingestor; a handful of aspirational tiles have neither) is **roadmap-labelled and non-connectable** — SAP/D365 are demand-gated for `2.0.1`, every other unshipped tile is `unscheduled`. `SHIPPED_CONNECTOR_IDS` and `ROADMAP_TARGETS` are EXPLICIT enumerations (like the frontend tile's `ENABLED_CONNECTOR_IDS`) so an unknown/test id is never mistaken for roadmap and wrongly blocked; `annotate_connector` stamps additive `roadmap`/`roadmapTarget` fields (never mutates status/tier). Applied as a serve-time overlay in `db.org_connectors_list`/`org_connector_get`, so the flags reach `GET /api/connectors`, the workspace-catalog, and the connect guard (`main.py connect_connector` refuses a roadmap connect with a named reason) without a reseed. Mirrors the Stack Builder registry's `RoadmapSystemConfig` (`industry_registry.py`, target `2.0.1`). The *dynamically-discovered* CI cross-check against `discovery/ingest/` (R191-R1 AC1) is a separate, later task; a static seed cross-check (`test_connector_roadmap_catalog.py::test_catalog_is_fully_classified`) keeps the enumeration honest meanwhile.

* `backend/app/context_assembly.py` + `assembly_policy_config.py` + `config/assembly_policy.json`: 2.0-B3 T1 (AC1) — the context assembler's precedence as **declared configuration**. R16-B2 built the assembler with the right discipline (a fixed, documented, deterministic rule sequence) but kept precedence IN CODE: the rank key was a hardcoded `(-confidence, -freshness, id)` and "observed beats inferred" was a boolean switching between two hardcoded orderings — so precedence was untunable, and **source type did not exist as a dimension at all** (a Slack thread and a ServiceNow incident competed on confidence alone, and the more confident chat won). Precedence now lives in `config/assembly_policy.json`; reordering its `ranking` changes composition with no code deploy. **The declaration distinguishes hard tiers from soft preferences**, because collapsing them would quietly weaken R16-B2 AC3: a dimension in `budget_partitions` is a HARD tier (a worse-tier item can never DISPLACE a better-tier item that fit), one in `ranking` is a soft preference within a tier. `origin` is hard by default (observed data must not be displaced by a guess); `source_type` is soft by default so a highly-relevant conversation is not shut out by the mere existence of one structured record — but moving it into `budget_partitions` makes it hard, which is the configurability the AC asks for. **Unknown values sort LAST, never first** (rank derived as `max+1` from the table, so it stays correct as the table grows) — an item earns precedence by declaring what it is, the same fail-safe rule the module already applies to provenance and undated freshness. The loader REFUSES an unknown dimension name (a typo would silently drop a precedence rule), a `ranking` not ending in `candidate_id` (the stable tiebreaker, without which the key is not a total order and determinism is lost), a dimension in both lists, a declared dimension with no rank table, and an out-of-range floor; a missing/invalid file RAISES rather than defaulting, because a deployment that thinks it configured precedence and did not composes findings differently from what its operators believe. `graph_context.py` is the one caller that DEGRADES instead (enrichment is non-blocking) — it falls back to the R16-B2 precedence and logs at ERROR naming the consequence. Every `selection_log` entry now carries `source_type` and `ContextPackage.policy_declaration` records the declaration, because a log read later has to be interpretable against precedence that is now editable. **Additive**: `AssemblyPolicy()` with no declaration behaves exactly as before T1; `AssemblyPolicy.declared()` is the opt-in. Source types (`structured`/`prose`/`code`/`conversation`) match the retrieval substrate's chunk content types plus the graph. See `docs/assembly_policy.md`.
* `backend/app/graph_context_builder.py`: ENT-4 graph context builder — turns raw graph traversal rows into a ranked, capped `GraphContext` for LLM prompts. Hard caps (15 entities / 20 relationships) and deterministic ranking are not configurable per-run. Distinct from `graph_context.py` (the ENT-3 run-KV enrichment bridge) — do not conflate.
* `backend/app/graph_constants.py`: single source of truth for the graph-context hard caps (`GRAPH_CONTEXT_MAX_ENTITIES=15`, `GRAPH_CONTEXT_MAX_RELATIONSHIPS=20`, `SPARSE_GRAPH_THRESHOLD=3`). Both `graph_context_builder.py` and `graph_context.py` import these — do not redefine the caps locally.
* `backend/app/routes_graph.py`: ENT-4 graph API routes — **registered** in `main.py` via `register_graph_routes(app)` (unlike `routes_sprint4_t5.py`). Four GET endpoints under `/api/graph`, all analyst+ and org-scoped via `get_current_org_id()` (request-body `org_id` is never trusted): `/opportunity/{opp_id}/neighbourhood`, `/entity/{entity_id}/neighbourhood` (both accept an optional `limit` query param for display-sized payloads), `/path`, and `/org/summary`.
* `backend/app/executive_report_engine.py`: executive report generation.
* `backend/app/learning_signals.py` + `learning_feedback.py` + `learning_signal_config.py` + `config/learning_signals.json` + `routes_learning_feedback.py`: 2.0-A3 T1 — the **learning signal set**: what the ranking-adaptation layer is allowed to learn from, and the weighting principle that separates this from click-tracking. **Exactly two sources**: analyst decisions (accept/dismiss/**defer-with-reason**) and 2.0-A2 outcome measurements — and *nothing* from `telemetry.py`, enforced structurally (`tests/unit/test_learning_signal_isolation.py` fails the build on any telemetry import, any telemetry name in executable code, or any read outside the permitted set; the guard is **proven to fail** — injecting an import turns three tests red). **An outcome outweighs an opinion**, enforced in TWO places because config validation alone was provably insufficient: (1) `validate_config` REFUSES a config where any decision weight reaches any non-zero outcome weight; (2) the **outcome floor** — a `below_band` (2.0) that is `weakly_comparable` (x0.5) with both caveat severities (x0.54) lands at 0.54, *below* a clean accept at 1.0, so caveated outcomes are floored at `outcome_floor_ratio` x the strongest decision weight. Justified, not convenient: a caveat says "this comparison is imperfect", not "this is not a measurement" (A2 T3's own rule). Floored BEFORE recency decay, since decay is identical for both classes — so at equal age an outcome always wins while a stale measurement and a stale opinion fade together. **A measurement with no projection still teaches**: when the verdict is `not_projected` the signal falls through to the MEASURED DIRECTION (`improved`/`worsened`/`unchanged`, taken from the `movement`-ROLE signal so a denominator moving is never read as the outcome) — weighted below the band verdicts (a direction with no expectation is weaker evidence) but above every decision, and never applied when a projection DOES exist because the band verdict already incorporates the direction and using both would count one measurement twice. Without this fall-through every finding created before 2.0-A1 shipped would be permanently unlearnable. **Caveats down-weight, never drop** (a zero comparability multiplier is refused — that is the blocking A2 T3 declined, one layer up); confounders apply once per SEVERITY present, not per caveat. Join key is `opportunity_identity`; a finding without one is SKIPPED, never mis-keyed under a run-scoped id. **Similarity is conservative and declared** — detector/pack/signal-concept only (concept from A1's `signal_registry`, not a second mapping), with deliberately NO "same pack" tier and nothing inferred from titles or narrative (the fuzzy inference 2.0-B2 refuses for entity resolution). **Cold start (AC4)** needs BOTH a weighted-signal count and a DISTINCT-IDENTITY count, so one enthusiastically-reviewed finding cannot switch learning on for an org; `SignalSet.is_active` is the gate T2 must consult. Every weight is config with a declared `basis` (almost all honestly `provisional` — no production outcome data exists yet) and is served by `GET /api/learning/config`. **T1 applies NO adjustment** — that is T2, and no route here returns an adjusted ranking. See `docs/learning_signal_set.md`.
* `backend/app/learning_adjustment.py` + `learning_adjustment_state.py` + `routes_learning_adjustment.py` + `database/models/ranking_adjustments.py`: 2.0-A3 T2 — the **bounded ranking adjustment**: a LAYER, not an edit. `discovery/scorer.py` (`_compute_impact`/`_rescale_impact`) and `cloud_ops_scorer.py`'s `ops_impact_rank` are BASE producers — they learn nothing and are unchanged; two structural guards pin the boundary from both sides (`tests/unit/test_base_scoring_does_not_learn.py` stops base scoring reaching the layer, `test_learning_signal_isolation.py` stops the layer writing scores/evidence/confidence/corroboration). **Applied at SERVE time**, which is what makes "base scoring untouched and always recoverable" structural rather than conventional: the stored order IS the base order, so disabling learning restores it with nothing to undo, and every served finding carries `_ranking.baseRank`/`baseImpact`. Applied BEFORE `with_display` — `with_display_scores` adds a per-id matrix offset (up to +0.6), and computing the score cap from that would make the cap vary by opportunity id for a cosmetic reason. **Exactly ONE adjustment function** (`adjust_ranking`; a test asserts it is defined in one module only) with two call sites — `main.list_opportunities::_apply_learned_ranking` and the roadmap serve path via `roadmap_engine.apply_learned_adjustment`. **`build_roadmap` is deliberately NOT an application point**: it runs during materialization and its output is PERSISTED, so adjusting inside it would bake the learned order into storage and disabling learning could not restore it (and materialization has no request tenancy context, so the org would be wrong). A1 T4's `_apply_projection_strength_rule` still runs at BUILD time — the capped-confidence demotion is a CORRECTNESS rule and learning is a PREFERENCE arriving after it. **TWO caps, both enforced**: `max_score_fraction` (0.15, proportional to base impact — the provable mathematical bound) and `max_rank_move` (3 — the customer-facing promise). The rank cap needs its OWN enforcement because capping each item's delta at N still permits ACTUAL displacement of ~2N through passive shoving (fuzz-verified), so placement uses the bounded-window `_bounded_placement` rather than a sort — the bound holds by construction. The sort key `(target, -rank_delta, base_index)` is load-bearing: without the middle tie-break term every single-rank move computes correctly and then changes nothing. **Clipping is recorded** (`wasCapped`/`cappedBy`/`requestedDelta`) — a clipped adjustment means the learned signal and the base scorer are in genuine tension. State is STORED (`ranking_adjustments` keyed `(org_id, detector_id, pack_id)` + append-only `ranking_adjustment_history`, migration `0037`), never derived at read time — a ranking that shifts as history accrues has no audit trail and nothing for T4 to reset; recomputation is an explicit POST and a contract test pins that serving a list never recomputes. Cold start is STORED as `learning_active=FALSE` rather than inferred. See `docs/ranking_adjustment.md`.
* `backend/app/learning_reason.py` + `learning_reason_vocabulary.py`: 2.0-A3 T3 — **why a finding moved**, as STRUCTURED DATA with the sentence rendered from it (A2 T4's confounder pattern: a prose string composed at the point of adjustment could not be counted, filtered or re-rendered). `AdjustmentReason` carries direction/magnitude, decision count + per-action breakdown, outcome count + per-verdict breakdown, `wasCapped`/`cappedBy`, `evidenceStrength`, and the LINKS; `render_reason` produces the `summary` that every surface shows, so none composes its own wording. **AC2's links are identifiers, not counts**: a decision resolves via `feedbackId` → `/api/learning/feedback/entry/{id}` (the payoff for T1 storing decisions with stable ids rather than widening a mutable enum), an outcome via `opportunity_identity` → `/api/opportunity-movement/{id}` carrying BOTH run ids and its `comparabilityVerdict` so a caveated measurement never presents as a clean one. T1's decision evidence ref gained `action`/`recordedAt` here, because "your team accepted 4 similar findings" cannot be rendered from a reason code. **The copy guard** mirrors A1 T5's `vocabulary.py` and blocks three categories: `knowledge_claim` ("we learned", "AgentIQ understands"), `importance_claim` ("more important", "should be prioritised", "we recommend") and — the subtle one — `credibility_implication` ("we are more confident", "your decisions corroborate this"), which would violate the SPIRIT of AC3 while passing its letter by implying the learned signal aided the finding's credibility. Deliberately NOT flagged: the counts, what the customer did, what A2 measured, and what was done — a guard that flags the evidence trains people to ignore it. Enforced at BUILD time (`render_reason` checks its own output) and at the BOUNDARY (contract tests sweep the served opportunity/explain/preview/roadmap payloads). **Placement is guarded too**: the reason is namespaced under `_ranking` and `reason_placement_violations()` fails if ranking copy leaks into `confidence`/`corroboration_*`/`evidenceIds`/`aiRationale`/`projection`. **Honest about thin evidence**: `evidenceStrength` is minimal/limited/moderate/substantial from a weighted count (an outcome counts double — for HEDGING only, never for the adjustment, which stays in T1's config), tuned so "three decisions and one measured outcome" reads as limited and says so. A finding that did not move carries NO reason (and `explain` 404s), because "this was not adjusted because…" on every unadjusted finding would bury the ones that were. See `docs/ranking_adjustment_explainability.md`.
* `backend/app/learning_feedback.py` storage note: the durable decision record is a NEW table (`opportunity_feedback`, DDL in `database/models/opportunity_feedback.py`, migration `0036`, mirrored in `provision.sql`), NOT a widened `("APPROVED","REJECTED","UNREVIEWED")` enum. Four reasons, decided deliberately: the existing `decision` field lives in the run-scoped `opps` KV blob that materialization rewrites and `replay.py` resets (a learning signal a replay can erase is not a signal — A2 T2's argument); it is keyed `(run_id, opp_id)` not on the stable identity; it has no per-decision id for AC2's links to resolve against; and the SAME literal tuple is validated for EVIDENCE decisions in `main.py`, where `defer` is meaningless. So the record is ADDITIVE — the analyst review flow is untouched and `set_opp_decision` mirrors `APPROVED`->`accept` / `REJECTED`->`dismiss` into it (non-blocking; a learning failure never breaks a review), while `UNREVIEWED` is deliberately NOT mirrored because clearing a decision is the absence of a judgement, not a third kind of one. APPEND-ONLY (no UPDATE/DELETE in the store, production REVOKEs both): changing your mind appends, because a store that edits its own history cannot answer "why was this ranked higher last month?". Reason codes are a CLOSED vocabulary — free text is refused (a reason the layer cannot group on teaches it nothing, and free text in a learning input is an unbounded PII surface); a defer with no reason is refused outright rather than defaulted, and the zero-weighted reasons (`no_capacity`/`blocked_by_dependency`/`awaiting_approval`) are the important ones — recorded and linkable, never learned from, because they are facts about the team's calendar rather than judgements about the finding. Audits `OPPORTUNITY_FEEDBACK_RECORDED` (registered in `middleware/audit.py` before its first emission site).
* `backend/app/outcome_confounders.py` + `outcome_confounder_config.py` + `config/outcome_confounders.json`: 2.0-A2 T4 — confounder detection: the labelled caveats that make A2's "measure movement, never claim credit" discipline into code (AC3). **Two rules govern every line**: (1) *never a silent adjustment* — nothing scales, weights or corrects a delta, because a quietly adjusted number cannot be reproduced by a customer holding the same source data; a structural test walks the AST and fails the build if any assignment to a delta-named target appears. (2) *never a blocked measurement* — detection only APPENDS caveats and has no return path meaning "do not publish"; a detector that raises is logged and skipped so one failure never costs the measurement its other caveats. Four detectors ship: `pack_version_change` (a field comparison, nearly free, and disproportionately important — a pack version bumps whenever detector/scorer/corroboration logic changes, so movement across a boundary may reflect a threshold edit; a missing version is an *advisory*, since absence of information is not evidence of change), `volume_shift`, `ci_population_change` (compares the resolved entity set via the shared `ENTITIES_VISIBLE_AS_OF_RUN_FROM_WHERE` clause, keyed on `entity_type:canonical_name` not the random per-row uuid; a 2.0-B2 merge/unmerge surfaces here as a caveat rather than looking like organic drift; a tiny estate uses an absolute-count rule because a fraction is meaningless at n=3), and `seasonality_window_mismatch`. **Caveats are structured data** (`type`/`severity`/`detail`/`detectedAt` + `thresholdBasis`), never prose, so T6 counts them and B1 renders them; `summarise_confounders` travels with the record and the counts are promoted to columns (migration `0034`). **Thresholds are configuration, not constants** — in `config/outcome_confounders.json`, each declaring `basis` as `measured`/`operationally_justified`/`provisional` (volume-shift and CI-population are honestly marked provisional), and the seasonality WINDOW DEFINITION is configurable (`calendar_month_overlap`/`fiscal_quarter`/`declared_periods`/`disabled`) because a hardcoded calendar is wrong for much of the customer base. **New confounder types are registerable** via `register_confounder_detector` — a test asserts the movement engine names none of the type codes, so adding one never requires editing the comparison engine.
* `backend/app/opportunity_movement_record.py` + `opportunity_movement.py` + `routes_opportunity_movement.py`: 2.0-A2 T3 — post-action monitoring: re-measure the signals a T2 baseline froze and store the comparison (AC2/AC5/AC7). **Three gates, all required before a measurement exists**: the lifecycle state must be one a recorded action put it in (`is_measurable`), a frozen baseline must exist, and a run must have landed STRICTLY AFTER the action date. Fail any and the answer is **no record — never a zero-delta one**; `MovementMeasurementSkipped` carries the reason so an empty outcome view is explainable. Everything anchors on the action date: there is deliberately no "most recent run" or "since creation" fallback, either of which would fold pre-action data into the delta. **Comparability is computed and CARRIED, never silently normalised** — `assess_comparability` assesses unequal window lengths, insufficient elapsed time vs A1's projected horizon, sparse post-action sampling, run-cadence gaps and seasonality mismatch; verdicts only ever escalate (`comparable` → `weakly_comparable` → `not_comparable`), a poor verdict still REPORTS with the caveat attached, and the DB column is `NOT NULL`. Re-uses the existing retrieval (`get_instances_by_identity` for the cross-run series, `temporal.get_run_signal_rows` for re-measured values, `signal_registry.lower_is_better` for direction) — no parallel matching or measurement path. Records are **stored artifacts, not computed-at-read views**, so a later pack change cannot retroactively alter a measurement already reported; idempotent per `(org_id, opportunity_identity, current_run_id)` (DO UPDATE — re-deriving one run pair corrects, it does not duplicate; contrast the write-once baseline). Shaped trace-friendly for 2.0-B1: both run ids are first-class columns, each signal keeps its own before/after pair, both windows and pack versions are retained. DDL in `database/models/opportunity_movements.py`, migration `0033`, mirrored in `provision.sql`. Read-only API, analyst+, org from tenancy middleware.
* `backend/app/opportunity_baseline_artifact.py` + `opportunity_baseline.py` + `routes_opportunity_baseline.py`: 2.0-A2 T2 — the IMMUTABLE measurement basis a finding is born with (AC1), frozen at creation. **Not the rolling temporal baseline**: `temporal.py`/`baseline_calculator.py` recompute `baseline_mean`/`baseline_stddev` over a sliding `BASELINE_WINDOW_DAYS` window, so they move every time the job runs — this artifact freezes a point-in-time copy so a comparison six months later is not against a moving target. Keyed `(org_id, opportunity_identity)` in its own `opportunity_baselines` table, deliberately NOT in run-scoped KV (`opps`/`evidence` are rewritten wholesale by materialization and by replay — `replay.py` resets `decision` on replay; a baseline a replay can rewrite is not a baseline). **Write-once, enforced three ways:** the primary key makes a rewrite a conflict, the store's only write is `INSERT … ON CONFLICT DO NOTHING` (never `DO UPDATE`) and contains no UPDATE/DELETE at all, and production REVOKEs UPDATE/DELETE on the table. A second capture is a reported no-op returning the STORED artifact, never the freshly computed one. The artifact carries signals (roles taken from the A1 `signal_registry` so T3 re-measures the same fields), the observation window with its **derivation recorded** (a fallback window must never look measured), the measured values, the frozen baseline stats, and `packVersion` — which T4's confounder detection reads to flag pack-logic drift, so dropping it breaks T4. It REFERENCES the originating `opportunity_instances` row rather than replacing it (that row is "how it scored on that run"; this is "the basis we will be judged against"). `has_baseline()` is T7's other gate. API is read-only (no POST/PATCH/PUT/DELETE), analyst+, org from the tenancy middleware. DDL in `database/models/opportunity_baselines.py`, migration `0032`, mirrored in `provision.sql`. **Backfill is out of scope** — a finding created before this shipped has no baseline and is therefore never measurable, which is the honest outcome.
* `backend/app/opportunity_lifecycle_states.py` + `opportunity_lifecycle.py` + `routes_opportunity_lifecycle.py`: 2.0-A2 T1 — the persisted opportunity lifecycle (`open → actioned → monitoring → measured`, plus `dismissed`/`stalled`). **Orthogonal to the review `decision` field** (`APPROVED`/`REJECTED`/`UNREVIEWED`): decision answers "is this real?", lifecycle answers "has the customer acted, and are we watching?" — never collapse them into one enum (a contract test pins that the store never reads `decision`). Keyed on `(org_id, opportunity_identity)` — the STABLE cross-run identity — NOT on the run-scoped `opps` KV, because lifecycle is a property of the problem, not of one observation; `ensure_tracked` is INSERT-ONLY so a run that re-surfaces a finding never resets its state. `opportunity_lifecycle_states.py` is the state machine **as data**: one explicit `TRANSITIONS` table (no scattered `if` checks), and illegal moves are refused with a NAMED reason listing the legal alternatives. **The non-inference rule is structural, not conventional:** `actioned` is absent from `SYSTEM_REACHABLE_STATES`, `record_action` takes `action_date` as a required positional arg with no default and hard-wires `ACTOR_HUMAN`, a missing/future/unparseable date is an error rather than a default, and there is no generic `PATCH {state}` route. `is_measurable()` is the gate T3/T7 must consult — never re-test states inline. History is append-only: an analyst unwinding a mistaken action appends a forward row rather than rewriting the mistake. DDL in `database/models/opportunity_lifecycle.py`, migration `0031`, mirrored in `provision.sql`. * `backend/discovery/signals/ops_stream.py`: MSP-B7/AT-669 (T1) dedup at admission — the FIRST of MSP-B7's five event-volume disciplines. `OpsEventStream.admit(event)` folds re-firing `OperationalEvent`s into ONE `ActiveSignal` per `(org_id, event_signature, resource, active period)`, maintaining an occurrence count (over DISTINCT provider event ids — a redelivery of an already-counted firing is idempotent) and a first/last-seen span; a stuck alarm firing every 5 min is one fact with count 288/day, not 288 facts. Deterministic (folding depends only on event fields, never arrival order: representative = earliest firing by `(observed_at, signal_id)`, count/span order-independent) and org-scoped (fold key includes `org_id`; cross-org admit/resolve raises `OrgScopeError`). The raw payloads are NEVER embedded — `ActiveSignal.resolve_raw_instances(store)` walks each folded firing's evidence pointer back to the raw-event store (AT-638) so an aggregate opens to its real instances (aggregation compresses volume, never evidence). Also HOSTS T4 (per-run budget, AT-672): the constructor takes `budget=N` and `admit` defers-and-counts events past the budgeted window via the injected `RunBudget` (see `budget.py`); `stream.budget_report()` returns the deferral proof. Volume-based (re-fires count too) and arrival-ordered (the budgeted window is the first `limit` events; deliberately order-dependent unlike the other stages). `BudgetReport` (`budget`/`processed`/`deferred`/`seen`/`breached`/`deferred_by_source`/`deferred_window`/`reason`, JSON via `to_dict`) is the run-record + R18-C2 content-panel artifact. `limit=None` (default) = unbounded. Stopping early is RESUME, not truncation: the advanced position rides the terminal batch's checkpoint, the stop logs at WARNING, and `poll_report()` names each undrained scope + the bound that stopped it (the runner merges it into the AWS health block as `poll` and degrades the reported status when `complete` is False). * `backend/discovery/ingest/aws_watermark.py`: MSP-B1 per-scope time positions for the AWS poll source — the resume-correctness core for the two time-series surfaces. `TimePosition` + `encode_position`/`decode_position`/`watermark_of`/`advance_ascending`/`advance_descending`. Two properties it exists to guarantee. (1) **No truncation loss**: CloudWatch is read `ScanBy='TimestampAscending'` so a page-budget cut-off is a complete PREFIX and the watermark can safely advance; CloudTrail is newest-first with no sort control, so while truncated the watermark is PINNED and a `ceiling` walks backwards through the older remainder (`pending_high` holds the eventual watermark until the window drains), with `PollPage.has_more` driving the continuation. Advancing past an unread backlog — the original behaviour — stranded those events permanently. **Only a genuinely drained window promotes `pending_high`**: a truncated read that yields nothing this position accepts (routine — CloudTrail delivery is eventually consistent and the management-event filter drops records) PINS the position and retries next run, because treating an unreadable page as a drained one closes the window over a backlog that was never read. For the same reason a same-instant ceiling is not automatically "no progress": newly-read ids AT that instant are carried forward into `ceiling_ids` (the mirror of `advance_ascending`'s same-instant merge) so the next poll excludes them and the walk continues; the walk pins, loudly, only when the instant yields nothing new. (2) **No boundary drops**: comparison is on PARSED instants (a boto3 `datetime`, `…Z`, and `…+00:00` are the same instant; string comparison said otherwise), and the position carries the provider event ids seen AT the watermark instant so a late-arriving same-second event is admitted while already-seen ones are not re-read (CloudTrail has second granularity and eventually-consistent delivery, so this is routine, not hypothetical). The descending walk is additionally bounded in DEPTH by `advance_descending(..., max_backfill_seconds=…)` — measured from the backfill's own `pending_high`, so it is independent of when the run happens; on reaching it the window CLOSES (promote `pending_high`, clear the ceiling) and logs at WARNING, because an unbounded initial walk of the 90-day `LookupEvents` retention pins the watermark across many runs and delays every new event behind the whole history. Events older than the depth are consequently not ingested — a declared, configurable initial-load boundary (`AWS_EVENT_MAX_BACKFILL_DAYS`), never a silent thinning. Wire format is backward-compatible: a position with nothing extra to carry encodes as the **plain ISO string** it always was. The checkpoint value stays opaque to the runner (R16-A1 AC5) — read it with `watermark_of`, never by comparing the raw string.

* `backend/discovery/signals/app_insights_signal.py`: 2.0-D3 **the single source of truth for the Application Insights signal vocabulary** — which records are App Insights operational signals, which of the four kinds each is (`availability` / `application_failure` / `dependency_failure` / `health_transition`), and which are excluded telemetry. * `backend/discovery/signals/reference_mappers.py` → **`map_app_insights`** (2.0-D3 T2): the B0 mapper. Accepts a record from EITHER D3 surface and resolves which from the record's own shape (`detect_surface`), so it stays standalone-invocable like every other reference mapper. Four things it gets right on purpose. (1) **Resource = the monitored application, never the alert rule** — the explicitly-supplied monitored-application reference when Azure gives one (`MONITORED_APPLICATION_FIELDS`), else the App Insights component; both explicit, nothing inferred. `resource_type` comes from the SAME shared `azure_resource_type_from_id` table every other Azure mapper uses (a `components` id → `monitoring`, an App Service id → `compute`); D3 deliberately adds no per-surface override, because a provider-specific carve-out in shared code is how that table stops being shared — and nothing downstream branches on `resource_type` (verified: only `cloud_ops_runtime.py:359` carries it as metadata). (2) **`event_class` maps D3's "alarm/health" wording onto B0's CLOSED vocabulary**: health transition → `state_change`; ACTIVE availability/application/dependency failure → `error`; a RESOLVED failure or an unclassifiable in-scope alert → `state_change`. Consequence stated rather than hidden: a firing and its resolution carry different classes and therefore different signatures — intended, since they are different operational facts, and it is what lets recurrence count firings without resolutions diluting the count. (3) **`event_type` is where the App Insights signal survives** the class collapsing to two tokens, so availability / application-failure / dependency-failure / health stay distinguishable. It is the KIND, not the customer's rule name, because two rules both reporting "availability of app X is failing" are ONE recurring operational fact and folding them is what stops MSP-B7 counting the same problem twice. **The one exception is deliberate**: an UNCLASSIFIABLE in-scope signal appends the rule name (`ApplicationInsights/Signal/<rule>`), because folding two unknown conditions would be an unjustified claim — the signature service guarantees genuinely different events get different signatures, and we cannot know two unknowns are the same fact. Both directions are pinned by tests. (4) **The signature comes from the shared service**, never computed here (a structural test asserts the mapper never calls `compute_event_signature` itself); `azure_app_insights` is registered in `event_signature._SOURCE_SYSTEM_FAMILY` → `azure`, without which the same fault would fingerprint differently depending on which Azure surface reported it. The payload is BOUNDED and curated (the complete Azure record lives only in the AT-638 raw-event store, reachable via the event's OBSERVED pointer) and deliberately introduces no `principal`/`actor`/`user`/`caller` key, since one of those would silently change what the fingerprint keys on. Golden fixtures pinning the ENTIRE normalised output for every supported event type: `discovery/tests/fixtures/app_insights_mapping_golden.json` (expectations hand-written from the spec, not dumped from the implementation, and the signature validated by RECOMPUTING it from stored components rather than pinning a hash). Documented in `docs/msp_operational_event_schema.md` §5.

* `backend/discovery/ingest/azure_app_insights.py`: 2.0-D3 T1 — the **bounded Application Insights read scope**. Deliberately NOT a connector: it adds no client, no credential type, no ARM surface and no endpoint, because the story's constraint is "App Insights alerts and health/failure events **via Azure Monitor surfaces already reached by B2**" — adding a surface here would be the "new connector family" D3 rules out. The rules it applies decide two things: (1) **is this in App Insights scope?** — only on an EXPLICIT `/providers/microsoft.insights/components/<name>` reference read from documented reference fields only (`alertTargetIDs`/`alertId`; `properties.impactedResources[].resourceId`/`resourceId`/`resourceUri`); there is no name matching or resource-group heuristic, and a different `microsoft.insights/*` type (metricalerts, actiongroups, webtests) is never mistaken for a monitored application. The ops-impact scorer (`cloud_ops_scorer.py`, MSP-B6 T4) ranks findings by config-driven ops impact across four dimensions (effort concentration = count × median TTR, breadth of services/CIs via B3, recurrence stability = steady vs burst, and automation shape = trivially-resolved outranks judgment-heavy); every weight/threshold loads from `cloud_ops_pack_config.json`'s `calibration` block (a weight change alters ranked order with no code deploy) and confidence is never recomputed — the detector's honest four-part-contract level is carried through. Wired in `runner.py` (ranked once per run before per-finding scoring). MSP-B6 T6 (AT-741) enforces the four-part contract AT THE PACK BOUNDARY: `cloud_ops_finding.enforce_pack_findings` runs in `runner.py` right after the cloud_ops detectors fire and raises `CloudOpsContractViolation` (failing the run) if any finding is missing a part or references an individual — not wrapped in a try/except, so the violation propagates. It also owns the graceful MSP-B5-absent degradation: the recurring-resolution-loop composite carries a runbook leg via `build_runbook_leg` — `documented_repeated_manual` when B5 runbook matching is present, else it degrades to `repeated_manual` with the explicit "runbook match unavailable" label (never silently narrower).
* `backend/discovery/packs/template_registry.py`: Stack Builder template registry (`TEMPLATE_REGISTRY`) on the R18-C1 generic `TemplateDefinition` model — a template is a bundle of EDITABLE defaults (systems, roles, focus, pack, terminology, metadata), never a fork of the engine, and adding one is a dict entry with no model/route/API change. Seven entries: `commercial_lending`, `financial_services_cloud` (2.0-D1 T4), `service_operations`, `insurance` (2.0-D2 T1), `revenue_operations`, `managed_cloud_operations`, `security_operations`. The **`insurance`** entry is the clearest demonstration of the model's genericity claim: D2 is explicitly a CONFIGURATION exercise, so it reuses `pack_id='service_cloud'` and adds NO detectors — claims handling, underwriting review and policy servicing are expressed purely through roles (Service Cloud as `system_of_record` for claims + policy-service records; ServiceNow/Jira as `workflow_system` for assignment and escalation history; Teams/Slack as `operational_signal_source` corroborating handoffs; Confluence/SharePoint as `documentation_system` for policy, procedure and underwriting context), focus (`member_customer_service`), and the insurance terminology set. **2.0-D2 T3** set the focus defaults: the canonical `member_customer_service` focus with six EXISTING emphasis tags mapping to the five areas D2 names (`service_casework` policyholder service, `intake_requests` claims intake, `approvals` + `compliance_risk` underwriting review, `backlog_work_queues` operational queues, `handoffs_routing` cross-team handoffs). It is a STARTING VALUE: an underwriting-heavy customer selects `approvals_compliance` and their choice wins, recorded as an edited field. Two semantics worth knowing. (1) The emphasis TAGS are declarative — `routes_stack_builder` returns them for pre-population and launch provenance captures them, but RANKING comes from `focus_id` alone through `FOCUS_AFFINITY`'s detector-id map, so emptying the tags changes no rank (a test proves it, the same discipline T1 applied to `detector_emphasis`). (2) Focus affinity ANNOTATES, never filters — a detector outside the active focus is "surfaced but not emphasised", so no pattern is suppressed and only relative ranking moves. `metadata.focus_limitation` REPORTS (T3's own instruction) that no single canonical focus emphasises all five areas: `member_customer_service` emphasises 2 of the pack's 7 detectors, claims handoffs live under `cross_system_handoffs` and underwriting review under `approvals_compliance`. Widening `member_customer_service`'s affinity would change ranking for every industry that uses it (STRS, FSC, `service_operations`), so it is deliberately not done — a focus spanning a whole industry workflow needs a separate focus-model story. **2.0-D2 T2** finalised that vocabulary as the story's reviewed candidate mappings — `customer`→policyholder, `account`→policy, `ticket`→service request, `approval`→underwriting review, `obligation`→coverage requirement, plus `backlog`→claims queue for queue coverage — stored ONLY on the template (no insurance wording in any detector, report builder, LLM branch or frontend component; tests sweep for it) and carried to every narrative surface by the unchanged serve-time engine. Three mapping-safety rules constrain it, all pinned by `test_insurance_terminology.py`: no replacement may contain its source (the "policy policy" malformation that shipped for FSC in 2.0-D1 T4), no replacement WORD may be another mapping's source (or repeated application cascades), and a mapping must not capture a word this product uses for something else. Four candidates are therefore deliberately REJECTED and documented inline so nobody re-adds them: `queue`→claims queue and `team`→claims team are superstrings yielding "claims claims queue"; `agent`→adjuster would rewrite the AI agent (blueprint `agentName` "Monitoring Agent" → "Monitoring Adjuster"); `case`→claim would mislabel a policy-endorsement case as a claim. **Honest limit on the observable effect** (recorded in `TestWhereTheVocabularyIsActuallyObservable`): the map rewrites every allowlisted field it is given, but `service_cloud` findings carry NO narrative fields at all (`ui_labels_path: None`, unlike nCino/FSC) and the platform's deterministic roadmap stage summaries contain none of the source words — so the vocabulary lands on LLM-generated narrative (`aiSummary`, `aiWhyBullets`, `aiRisks`, `aiSuggestedNextSteps`, `aiExecutiveSummary`, `executiveSummary`) rather than on finding titles. Giving `service_cloud` a label file would change output for every Service Cloud industry and is outside D2's configuration-only scope. Its `metadata.industry_id` is `insurance`; **2.0-D2 T4** added the matching `INDUSTRY_REGISTRY['insurance']` entry (see the industry_registry note below) with the SAME canonical system ids and roles as this template, so the two never disagree about the primary pack (`service_cloud`) or the workflow shape — `test_insurance_anchoring.py` pins that equality. ## Runtime And Env Notes

* Backend `.env` and frontend `.env` are intentionally untracked. Use `backend/.env.template` as the setup reference.
* Backend database is PostgreSQL, configured via `DATABASE_URL`. Contract tests use a dedicated `*_test` database derived from `DATABASE_URL` (or `TEST_DATABASE_URL`); they never touch the dev DB. `DB_POOL_MIN` / `DB_POOL_MAX` tune the `db.py` connection pool.

* Optional LLM features use `ANTHROPIC_API_KEY`; deterministic fallbacks should still work without it.

## Architecture Notes

* The API protects most endpoints with `require_auth`; tests usually pass `Authorization: Bearer dev-token-change-me`.
* PostgreSQL stores most tables as `{ id, payload }` JSON rows, plus `runs`, `run_events`, and run-scoped KV entries. `backend/app/db.py` handles this layer, serving every query from a process-wide connection pool (see the `db.py` entry above).
* `backend/database/connection.py` is a separate psycopg2 layer (telemetry connection/session helpers). Do not conflate with `db.py`; it does not share the `db.py` pool.
* Run lifecycle starts at `POST /api/runs/start`, then materialization writes status, events, opportunities, evidence, clusters, roadmap, executive report, and enrichment into run-scoped storage.
* Replay should re-serve persisted artifacts only. It must not call live ingestion or regenerate LLM output.
* LLM enrichment is advisory post-processing. It must not mutate scoring fields such as impact, effort, tier, decision, or evidence IDs.
* `OppEnrichment.relationships` is intentionally different from the other enrichment fields: it is read live from `entity_relationships` through `graph_query.py`, not from a run-scoped KV artifact. The graph is cross-run state, so later relationship upserts can change what a historical run's relationship view returns.
* `OppEnrichment` also carries ENT-2 cross-system corroboration fields (`corroboration_sources`, `corroboration_label`, `triple_corroboration`, `corroboration_rule_ids`), populated from the stored opportunity record. See `backend/app/corroboration_engine.py` and `backend/discovery/packs/corroboration_rules.py`.
* Operational-app friction is first-class OBSERVED evidence: **COR-09** (Java, keyed `java_app`) and **COR-10** (.NET, keyed `dotnet_app`) are *elevating* corroborators (MEDIUM→HIGH like ServiceNow/Jira), not Slack-capped. They are gated on the source being connected and only fire when the source's `operational_friction` block is fresh; a lone operational source stays MEDIUM (single-source, COR-08). Java and .NET share the SAME signal language (via `operational_signals.py`), so their corroboration behaviour is identical by construction — adding a third operational platform means: new adapter/ingestor over the shared base + a new parallel COR rule (rule registry + engine check + `_CORROBORATION_RULE_SYSTEMS` + label priority + a contract test), nothing else.
* Pack selection is centralized in `backend/discovery/packs/pack_config.py`. Current packs: `service_cloud`, `ncino`, `financial_services_cloud`, `strs_benefits`, `sqlserver_opsignal`, `github_engineering`, `enterprise_ops`, `cloud_ops`, `security_ops`. The `cloud_ops` (Cloud-Operations Discovery, MSP-B6) pack keeps its calibration values, detector thresholds, and NOC terminology set in the external `cloud_ops_pack_config.json` (loaded via `cloud_ops_config.py`) so a config change alters behaviour with no code deploy. Its five detectors — four record/stream detectors (`cloud_ops_recurring_resolution_loop`, `cloud_ops_alert_triage_toil`, `cloud_ops_reassignment_ping_pong`, `cloud_ops_queue_ageing`, MSP-B6 T2) plus the shared-CI hotspot (`cloud_ops_shared_ci_hotspot`, T3: depth-bounded traversal over B3 dependency edges + window-gated event corroboration) — read the ITSM/event block at `sn_data['cloud_ops']` and emit findings carrying the four-part contract built by `discovery/packs/cloud_ops_finding.py` (evidence, confidence, corroboration, source trace; groups/queues/services/CIs only — never individuals). `cloud_ops_finding.py` also owns the causal-gate: hotspot wording is concentration-shaped ("incidents concentrate on a shared dependency...") and validated NEVER to be causal ("caused by...") — causality is reserved for the causal engine. The ops-impact scorer (`cloud_ops_scorer.py`, MSP-B6 T4) ranks findings by config-driven ops impact across four dimensions (effort concentration = count × median TTR, breadth of services/CIs via B3, recurrence stability = steady vs burst, and automation shape = trivially-resolved outranks judgment-heavy); every weight/threshold loads from `cloud_ops_pack_config.json`'s `calibration` block (a weight change alters ranked order with no code deploy) and confidence is never recomputed — the detector's honest four-part-contract level is carried through. Wired in `runner.py` (ranked once per run before per-finding scoring). MSP-B6 T6 (AT-741) enforces the four-part contract AT THE PACK BOUNDARY: `cloud_ops_finding.enforce_pack_findings` runs in `runner.py` right after the cloud_ops detectors fire and raises `CloudOpsContractViolation` (failing the run) if any finding is missing a part or references an individual — not wrapped in a try/except, so the violation propagates. It also owns the graceful MSP-B5-absent degradation: the recurring-resolution-loop composite carries a runbook leg via `build_runbook_leg` — `documented_repeated_manual` when B5 runbook matching is present, else it degrades to `repeated_manual` with the explicit "runbook match unavailable" label (never silently narrower).
* **Pack invariants — pack versioning (R16-B1 §4):** every pack declares a `packVersion` in `PACK_REGISTRY` (resolved via `get_pack_version()`), and it is stamped onto every opportunity instance so pack governance (1.9) can later tell a *data* change from a *pack logic* change. This signal is only useful if the version actually moves: **bump a pack's `packVersion` in `pack_config.py` whenever you change that pack's detector, scorer, or corroboration-rule logic** — treat it as part of the PR checklist for any pack change. Use semantic bumps (patch for tweaks, minor/major for behaviour changes). Two runs stamped the same version must be reproducible from the same data.
* **Multi-pack discovery runs (R191-P1):** a run may select `pack_ids: List[str]` (order-preserving, deduplicated via `pack_config.normalize_pack_ids`) instead of a single `pack`; `discovery/runner.py` runs every selected pack's detectors against the ONE shared normalised signal, with each pack's OWN scorer calibration applied only to that pack's findings — never blended (AC3). A single-pack run is byte-identical to the pre-multi-pack pipeline (AC2). No cross-pack merging: two packs can both surface a given detector as two distinct findings, distinguished by `opportunity_identity` (which includes `pack_id`) — an explicit, permanent non-goal (AC4). **T3 — provenance tagging (AC1/AC6):** every finding (`opp["packId"]`/`packVersion"`, pre-existing via R16-B1 §4) and now every EVIDENCE ITEM (`discovery/evidence_builder.py::build_evidence()` and the inline Jira/ServiceNow corroboration evidence built directly in `runner.py`'s pack loop — a separate code path that doesn't go through `build_evidence()`) carries the `packId` of the pack that produced it; a roadmap entry is just an opportunity referenced (not reconstructed) by `app/roadmap_engine.py::build_roadmap()`, so it inherits `packId`/`packVersion` for free. The run record carries `packIds` (list), `packVersions` (dict keyed by packId), and `packs` (full per-pack execution metadata) alongside the backward-compatible singular `packId`/`packVersion` scalars (which mirror the PRIMARY/first-selected pack). `frontend/src/types/analystReview.ts`'s `OpportunityCandidate` and `frontend/src/types/partialResults.ts`'s `EvidenceReview` both gained optional `packId`/`packVersion` fields (contract v1.11) — additive, so pre-v1.11 runs simply omit them.
* nCino, STRS, and `github_engineering` packs have compliance guardrails. Do not suggest automated credit/benefit decisions or automated merge approvals, branch deletions, or code changes; keep humans responsible for final decisions.
* Multi-tenancy is enforced via `middleware/tenancy.py`. Every request is scoped to an org; the default local org is `default`.
* RBAC is enforced via `rbac.py`. The dev user is seeded as owner of the default org on startup via `seed_owner`. Use `require_role` to gate privileged routes.
* Audit trail is enforced via `middleware/audit.py`. All mutating requests are logged automatically.
* A background connector health check job starts on app startup (`jobs/connector_health.py`) and shuts down on SIGTERM. Do not block startup waiting for connectors.
* A background baseline calculator job (`jobs/baseline_calculator.py`) recalculates scoring baselines on a configurable interval.
* A background OAuth token-refresher job (`jobs/token_refresher.py`) proactively renews vault tokens before they expire so connected sources stay live without the user re-running the OAuth flow. It only refreshes rows that hold a refresh token and have not previously failed; a genuine failure is left as `refresh_failed` for the user to reconnect.
* Telemetry events are tracked via `telemetry.py`. Do not log sensitive field values (tokens, PII) in telemetry events.
* Telemetry has a locked write signature: `record_event(event_type, payload)`. The `event_type` must be in `REGISTERED_EVENT_TYPES` — `record_event()` raises `ValueError` for an unregistered type. Register new event types (and their payload schema) before emitting them.
* Entity extraction (`entity_extractor.py`) is a non-blocking Stage 2 step — failures are logged and never break the run. Resolution (`entity_resolution.py`) is conservative and uses an N+1 lookup for ambiguous rows. Never write `canonical_name` from caller-supplied values; it is normalized internally. Display filtering uses `ENTITY_MIN_RUN_COUNT`, imported from `database/models/entities.py` — import it, do not redefine the threshold locally.
* `_verify_db_driver_imports()` runs at app startup to surface Oracle/PostgreSQL driver install problems early; it logs availability and does not block startup.
* The native DB connector subsystem (`backend/connectors/db/`) supports Oracle, PostgreSQL, and SQL Server. All queries must go through `query_guard.py` for injection prevention.
* The token vault (`auth/vault.py`) uses Fernet symmetric encryption. Set `CREDENTIAL_VAULT_KEY` before storing any connector credentials in production.
* The frontend should fetch backend data through `frontend/src/lib/apiClient.ts` or typed wrappers in `frontend/src/api/`.
* Avoid direct frontend imports of backend seed data or fixture JSON unless a test explicitly owns that fixture.

## Contract Rules

* If changing a backend response consumed by the UI, inspect the matching `frontend/src/types/*` type and `contracts/API_CONTRACT.md`.
* Any `frontend/src/types/*.ts` schema change requires a corresponding contract update and version bump.
* New run-scoped data should live under `/api/runs/{runId}/...`.
* Missing fields should generally be added by the backend to match the contract, not papered over in the UI.
* Audit lists are newest-first.
* Decision enums use uppercase values: `APPROVED`, `REJECTED`, `UNREVIEWED`.
* Readiness/status enums use the casing already defined in the relevant frontend type or contract.
* Contract changes require a version bump (e.g. v1.0 → v1.1) and PR sign-off by both the FE and BE leads, per the "Contract PR sign-off" section of `contracts/CONTRACT_RULES.md`.

## Frontend Conventions

* Keep UI changes consistent with existing page/component structure. This app is an operational tool, so favor dense, scan-friendly layouts over marketing-style sections.
* Use existing common components in `frontend/src/components/common/` when possible.
* Preserve route redirects in `frontend/src/App.tsx` unless the task is explicitly navigation cleanup.
* Keep API calls typed, handle `ApiError`, and avoid hardcoded localhost outside dev fallbacks.
* When changing user-visible flow behavior, update or add Vitest tests under `frontend/src/__tests__/`.

## Backend Conventions

* Register new route modules from `backend/app/main.py` following existing route-registration style.
* Use Pydantic response models for contract-sensitive routes where practical.
* Use `db.run_kv_get` and `db.run_kv_set` for run-scoped artifacts.
* Keep offline mode deterministic and usable without live credentials.
* Live connector failures should usually degrade to fixture/partial/error status rather than crashing the whole run, unless a test or contract says otherwise.
* Do not add duplicate endpoint registrations without checking FastAPI route order and existing tests.
* When adding a new connector, follow the secret naming convention in `backend/app/auth/README.md` (`{CONNECTOR_NAME}_CLIENT_SECRET`) so that `secrets.py` resolution works automatically.

## Security And Data Hygiene

* Never print full tokens, private keys, or `.env` contents.
* Connector credentials live in the database (Fernet-encrypted in the `credentials` vault table); there are no provider key files to manage. Treat any stray `*.key`/token JSON as sensitive and never commit it.
* `CREDENTIAL_VAULT_KEY` must never be committed. Add it only to production secrets management.
* Generated `.db`, `.venv`, `node_modules`, build output, and token JSON files should stay untracked.
* If a real credential file appears outside ignored paths, ask before moving it and suggest adding a precise `.gitignore` entry.

## Known Gotchas

* `routes_sprint4_t5.py` exists in `backend/app/` but is **not registered** in `main.py`. Routes defined in it are silently inactive — always verify `main.py` registrations before assuming an endpoint exists.
* `PATCH_materialize_t2_t6.py` is a patch/migration file in `backend/app/`, not a regular module. Do not import it as a route or service.
* `routes_stack_builder.py` and `routes_stack_builder_launch.py` both exist with different responsibilities. Check `main.py` before editing either.
* `materialize_t3_hook.py` is a separate T3 materialization step, not an extension of `materialize_t2.py`. Do not merge them.
* `run_store.py` and `db.py` both deal with runs but have different scopes: `run_store.py` handles start/read of run records; `db.py` handles broader KV and table access. Do not consolidate without checking all callers.
* `backend/database/connection.py` (psycopg2 telemetry helpers) and `backend/app/db.py` (pooled psycopg2 access) are different layers with independent connections. Mixing them will cause session/connection conflicts.
* Two migration directories (`alembic/` and `migrations/`) serve overlapping purposes. Use `migrations/` for all new work — `alembic.ini` already points there.
* The CORS middleware allows any `localhost` port via regex in addition to the explicit origins list. This is intentional for dev flexibility.
* `backend/connectors/db/query_guard.py` must be invoked for every native DB query. Skipping it bypasses SQL injection protection silently.
* `auth/vault.py` requires `CREDENTIAL_VAULT_KEY` to be set in production. A missing key causes connector secret storage to fail or silently fall back to plaintext.
* `get_pack()` falls back to `service_cloud` for an unknown pack_id (it logs a WARNING rather than raising). A typo'd pack id therefore yields Service Cloud detectors instead of an error — check the log line if a run produces unexpected detectors.
* **There are now THREE distinct "decision" concepts on an opportunity, and they are not interchangeable.** (1) the run-scoped review `decision` (`APPROVED`/`REJECTED`/`UNREVIEWED`, in the `opps` KV blob) answers "is this finding real?"; (2) the 2.0-A2 T1 `opportunity_lifecycle` state answers "has the customer acted, and are we watching?"; (3) the 2.0-A3 T1 `opportunity_feedback` record answers "is this finding type worth our team's time?" and is the only one the learning layer reads. Only (2) and (3) are keyed on the stable `opportunity_identity` and survive a run; (1) is rewritten by materialization and reset by replay. Never collapse any two of them.
* `record_event()` raises `ValueError` for an unregistered `event_type` — this is a deliberate change from the earlier silent-drop behavior. A new event type must be added to `REGISTERED_EVENT_TYPES` before it is emitted, or the call raises.
* `ensure_entities_table()` is startup-only — it creates the entities table once when `routes_entities` is registered. Do not call it per-request.
* **ServiceNow `sysparm_display_value=all` returns every field as `{value, display_value}` — the two are not interchangeable.** `discovery/ingest/servicenow.py` has two accessors and picking the wrong one is a live-only bug (offline fixtures store plain scalars, so tests pass either way): `_optional_sn_text` prefers the human DISPLAY value (correct for names, groups, states, operational status) and `_optional_sn_raw_text` returns the RAW value (required for `sys_class_name` — raw `cmdb_ci_netgear` vs display "Network Gear" — and for EVERY datetime field, whose raw value is canonical `YYYY-MM-DD HH:MM:SS` UTC while the display value is rendered in the instance's date format and the user's timezone). Checkpoint cursors, delta windows, and time-to-resolve math all depend on the raw form.
* **A missing ServiceNow table is `unavailable`, not an error.** The MSP-B11 SecOps tables (`sn_si_incident`, `sn_vul_*`) exist only where the Security Incident Response / Vulnerability Response plugins are activated, and are readable only by a role the integration user may lack. `ServiceNowClient.table_available()` pre-flights each one (memoized per client) and the stream degrades to `status='unavailable'` with a named reason, no `error`, and no checkpoint movement — so it resumes cleanly if the module is later activated. `discovery/runner.py` reports these on `sn_data["servicenow_unavailable_tables"]` and does NOT flip the ServiceNow stage to partial for them. Transport failures still translate to `ServiceNowIngestError`; keep the request URL out of the message (it embeds the whole encoded query and is rendered verbatim in run health).
