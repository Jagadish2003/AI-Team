# AgentIQ Claude Instructions

## Purpose

AgentIQ is a full-stack discovery and opportunity-analysis app. The backend ingests enterprise system signals, detects workflow/friction patterns, scores opportunities, materializes run-scoped artifacts, and serves contract-shaped API responses. The frontend is a Vite React app that guides users through integration setup, discovery runs, source intelligence, opportunity review, pilot roadmap, agent blueprint, and executive report views.

Keep this file short and actionable. Prefer reading the relevant code and contract files over relying on this file for every detail.

## First Rules

* Protect user work. Check `git status --short --branch` before edits and do not revert unrelated changes.
* Do not commit secrets, generated databases, local env files, token files, or server keys.
* Preserve API response shapes. `contracts/API_CONTRACT.md` and `contracts/CONTRACT_RULES.md` are the source of truth when frontend and backend disagree.
* Run-scoped endpoints must include `runId` in the URL. Do not add "latest run" fallbacks.
* Before editing shared behavior, inspect existing route/context/test patterns and make the smallest compatible change.
* After code changes, run the narrowest relevant tests first, then broader tests when the change affects contracts, shared API helpers, routing, or pipeline behavior.

## Tech Stack

* Backend: Python 3.11, FastAPI, Pydantic, PostgreSQL (psycopg2) with `{ id, payload }` JSON payload tables, pytest.
* Frontend: React 18, TypeScript, Vite, React Router, Tailwind, Vitest, Testing Library.
* Data/pipeline: offline fixtures by default, optional live Salesforce/ServiceNow/Jira/nCino ingestion, pack-aware detectors and LLM enrichment.
* Auth: bearer token via `DEV_JWT`; default local token is `dev-token-change-me`.

## Repository Map

### Backend — App

* `backend/app/main.py`: FastAPI app, CORS, core API routes, route registration. Check here first to confirm any route module is actually registered.
* `backend/app/routes_*.py`: feature route modules. Registered modules include stack builder, stack builder launch, run lifecycle, replay, normalization, enrichment, blueprint, workspace catalog, connector/product APIs, temporal, DB connectors, and connector auth.
* `backend/app/salesforce_product_packs.py`: 2.0-D1 T5 single source of truth for **which pack serves which Salesforce product** — the PACK-level half of the anchor-on-shipped rule. The R191-R1 guard resolves the domain-specific product ids (`salesforce_fsc`, `salesforce_sc`, …) through `IMPLEMENTATION_ALIASES`, where they map to `{salesforce}`; that answers the CONNECTOR question ("can we authenticate and read from this org?") but NOT the pack question ("do we read this product's objects and detect its patterns?"). Before 2.0-D1, `salesforce_fsc` was already a PRIMARY `system_of_record` for `financial_services` and CI was green while no FSC pack, detectors or ingest existed — the alias hid it. Each product now declares its pack with a `kind` of `DEDICATED` (its own domain pack: `salesforce_sc`→`service_cloud`, `salesforce_ncino`→`ncino`, `salesforce_pss`→`strs_benefits`, `salesforce_fsc`→`financial_services_cloud`) or `GENERIC` (deliberately served by `service_cloud` because no domain pack exists — `salesforce_rc`, and `salesforce_hc` whose pack is explicitly deferred to 2.0.1), each with a required `reason`. The rule the guard enforces (`test_r191_r1_ingestor_registry_enforcement.py::TestPackLevelCapabilityGate`) is: a domain-specific product presented as connectable must declare a pack here AND that pack must be registered — so an undeclared claim, or one naming a non-existent pack, fails. `pending_domain_pack()` records the still-generic products so the remaining gap is visible rather than implied. This is the BACKEND source of truth; the frontend's `CLOUD_PACK_REGISTRY` (`StackBuilderPage.tsx`) is what actually selects packs at launch and a contract test pins the two together — a registry entry honestly gated as FSC-capable while the frontend selected `service_cloud` would be the same dishonesty relocated (2.0-D1 T5 fixed exactly that: `salesforce_fsc` now selects `financial_services_cloud`, so declaring FSC activates the FSC pack instead of falling back to generic Service Cloud detection). The gate is **proven to fail**, not just asserted: removing the FSC pack registration turns it red (verified by experiment and pinned by `test_gate_goes_red_when_a_declared_pack_is_unregistered`), because a gate never observed failing is not known to be a gate.
* `backend/app/connector_roadmap.py`: R191-R1 T5 (AT-726) single source of truth for the **anchor-on-shipped** rule on the Integration Hub connector catalog. A catalog tile whose ingestion does not ship yet (SAP/`dynamics365` have an auth/config but no ingestor; a handful of aspirational tiles have neither) is **roadmap-labelled and non-connectable** — SAP/D365 are demand-gated for `2.0.1`, every other unshipped tile is `unscheduled`. `SHIPPED_CONNECTOR_IDS` and `ROADMAP_TARGETS` are EXPLICIT enumerations (like the frontend tile's `ENABLED_CONNECTOR_IDS`) so an unknown/test id is never mistaken for roadmap and wrongly blocked; `annotate_connector` stamps additive `roadmap`/`roadmapTarget` fields (never mutates status/tier). Applied as a serve-time overlay in `db.org_connectors_list`/`org_connector_get`, so the flags reach `GET /api/connectors`, the workspace-catalog, and the connect guard (`main.py connect_connector` refuses a roadmap connect with a named reason) without a reseed. Mirrors the Stack Builder registry's `RoadmapSystemConfig` (`industry_registry.py`, target `2.0.1`). The *dynamically-discovered* CI cross-check against `discovery/ingest/` (R191-R1 AC1) is a separate, later task; a static seed cross-check (`test_connector_roadmap_catalog.py::test_catalog_is_fully_classified`) keeps the enumeration honest meanwhile.
* `backend/app/db.py`: PostgreSQL (psycopg2) access, run records, run events, run-scoped KV helpers. Broad table access. Connections come from a process-wide pool via `connect()` — the returned object is a `_PooledConnection` proxy whose `.close()` returns the connection to the pool instead of closing the socket, so `closing(connect())` / `conn.close()` recycle. Pool size is tuned by `DB_POOL_MIN` (default 1) / `DB_POOL_MAX` (default 16). `org_connectors_list`/`org_connector_get` stamp each row with the R191-R1 T5 roadmap flags via `connector_roadmap.annotate_connector`.
* `backend/app/run_store.py`: run read/start helpers. Handles start and retrieval of run records only — do not consolidate with `db.py` without checking all callers.
* `backend/app/materialize_t2.py`: run materialization, status, audit, events, roadmap/report persistence.

* `backend/app/entity_extractor.py`: Stage 2 knowledge graph orchestration. Non-blocking — extraction failures are logged and never break the run.
* `backend/app/entity_resolution.py`: conservative entity resolution engine. Uses an N+1 lookup pattern for ambiguous rows; only confident matches are merged. `canonical_name_for()` is the PUBLIC alias of its canonicalisation — the cross-source engine imports it rather than re-implementing it, so the two layers cannot disagree about what a name is.
* `backend/app/cross_source_resolution.py`: 2.0-B2 T1 — the **ranked** cross-source resolution engine (the same service/team appearing in ServiceNow, Jira, Salesforce, code, and cloud events as several unrelated entities). Three tiers, consulted strongest-first, first decisive tier wins: `explicit_reference` (the source data cites the other entity's `(source_system, source_record_id)`, or both cite the same third-party record) → **auto-merge**; `alias_mapping` (the org's Owner-managed table — a recorded human assertion) → **auto-merge**; `name_similarity` (EXACT normalised name + a corroborating OBSERVED shared-neighbour relationship + a different source system) → **proposal only, never merged**. That last boundary is STRUCTURAL, not conventional: `AUTO_MERGE_TIERS` excludes the name tier, `action_for_tier()` is the single decision point and fails closed for any unknown/future tier, `ResolutionPolicy` has no field that can cross the boundary, and there is deliberately no env var and no `force` parameter (a test sweeps every policy permutation). Four gates run first — org (cross-tenant candidates are dropped and COUNTED), entity type, self, and status (an `ambiguous` row is never a merge target: merging onto the standing engine's recorded uncertainty would launder it into confidence). Ambiguity never merges and never falls through to a weaker tier — 2+ targets is recorded with every colliding candidate. Layering mirrors `trace_graph.py`: the engine is PURE (no DB, no clock, no writes) and the DB-backed loaders (`load_resolution_entities` / `load_relationship_index` / `resolve_org_entity_type`) sit at the bottom, org-scoped in SQL. **T1 DECIDES and writes nothing** — applying a merge with its provenance, the proposal review workflow, unmerge, and the corroboration uplift are the later 2.0-B2 tasks. Cross-references are read ONLY from the three documented metadata forms (`cross_references`, `external_ids`, and the enumerated `KNOWN_CROSS_REFERENCE_KEYS`); a reference is never inferred from a field that merely looks like an id, and `correlation_id` is deliberately excluded because its target system is per-org config. Rules documented in `docs/cross_source_entity_resolution.md`.
* `backend/app/corroboration_identity_gate.py`: 2.0-B2 T6 — the cross-source corroboration identity gate (AC5). Two independent systems agreeing is the platform's strongest confidence signal, and before T6 COR-01/COR-02 fired on a DETECTOR link with no identity check — so a ServiceNow team "Payments" and a Jira project "Payments" produced "Corroborated across ServiceNow and Jira" and a HIGH. **A same name is not a shared identity.** The gate engages only when both cross-source rules fired AND the two sides' entity references claim one identity (equal normalised names, different sources); it then requires the identity to be GENUINELY RESOLVED, strongest-first: same entity row → **not a pair a person UNMERGED** (2.0-B2 T7: every basis below outlives a reversal by design — a confirmed proposal stays confirmed and the source cross-reference is still in the data — so before this check a reviewer reversed a merge and the finding kept the HIGH it was given for the identity they just reversed; `graph_identity_resolver` now consults `entity_unmerge.merge_block_for` first, the same rule `apply_merge` follows, with the same-row short-circuit deliberately ABOVE it since one row is not a pair, and a released block restoring the elevation so the check is not a one-way ratchet) → the same T2 merge survivor (authoritative — reported with the rule its provenance recorded, because an alias table edited after a merge could make a re-derivation disagree with what the graph did) → a T3 human confirmation → a T1 auto-merge re-derivation. A name match can NEVER be a basis: `RESOLVED_BASES` has no name entry, the re-derivation asks T1 for a *merge* (whose name tier is structurally incapable of producing one), and a test pins `RESOLVED_BASES` against T1's `AUTO_MERGE_TIERS` so the gate cannot drift into trusting something T1 does not. **Fails CLOSED**: an identity claim that is not positively resolved never elevates — unresolved, resolver error, or no resolver alike — because elevating on an unreadable graph would reopen the hole exactly when the system is unhealthy, and a wrong HIGH is the harmful direction. The single fail-OPEN path is the module failing to import (a packaging fault CI catches), logged with the consequence named. Blocking removes the ELEVATION, not the evidence: COR-01/COR-02 stay on the result. Corroboration that made no identity claim (a ServiceNow *team* vs a Jira *process*) is deliberately untouched — T6 is not licence to silently downgrade the pre-existing detector-linked basis — but every result carries `identity_gate.identity_verified` so a reviewer can tell a proven-identity HIGH from a shared-detector one. Wired into `corroboration_engine.evaluate_corroboration` via `_apply_identity_gate`; `identity_resolver` is an injection seam so the gate is testable DB-free.
* `backend/app/entity_merge.py` + `routes_entity_merges.py`: 2.0-B2 T2 — the ONLY place a resolution decision becomes a change to the graph (T1 decides and writes nothing; T3 records a human answer and writes nothing to the graph). A merge writes `metadata.merge_provenance` on the SURVIVOR and a `metadata.merged_into` pointer on the constituent — never a delete. Three provenance rules: the constituent list is COMPLETE (the survivor's own identity is in it as `is_origin`, so `source_systems` is the full set of systems the node speaks for — what the T5 corroboration uplift must be able to trust); the rule is recorded PER CONSTITUENT (a node merged by three rules on three days by three actors cannot be described by one rule field) and an earlier rule is never rewritten by a later merge; and a human confirmation is its OWN rule (`confirmed_proposal`), never the tier that proposed it — a name match cannot authorise a merge, the person who confirmed it did. `choose_survivor` is deterministic (existing survivor → stable `source_record_id` → oldest → lowest id, a total order, so a re-run never rewrites history); merges compose transitively (both sides resolve to their current survivor first, cycle-guarded) and applying twice writes once (`already_merged`). Deliberately does NOT delete rows/edges, change `resolution_status` (a different fact from "this was merged"), or hide a constituent from any list — grep guards pin the first two. `_RULE_FOR_TIER` is a second, independent gate behind `AUTO_MERGE_TIERS`: a tier with no rule cannot merge here either. Applying is an explicit step (`POST /api/entity-merges/apply`), NOT wired into the discovery run — a merge is irreversible until unmerge ships. Every merge emits the `entity_merged` audit event. No schema change: provenance rides the existing `entities.metadata` JSON, so it travels with `GET /api/runs/{runId}/entities` too.
* `backend/app/entity_match_proposals.py` + `routes_entity_match_proposals.py`: 2.0-B2 T3 — the Owner/Analyst review surface for the PROPOSALS the ranked engine refuses to merge (tier 3 only; an auto-merge decision has nothing to review). Three rules: **one question per pair** (`proposal_id_for` hashes the ORDER-INDEPENDENT pair, so the engine's symmetric A→B / B→A proposals collapse into one row and a re-scan upserts rather than duplicating); **an answered question is never asked again** (the `ON CONFLICT` update is gated on `status = 'pending'`, so a later scan can neither revert an answer nor overwrite the evidence it was given against — the count left alone is REPORTED as `skipped_already_decided`, never hidden); and **recording a decision is not applying one** (`confirmed_pairs()` is the handoff a future merge applier consumes — this module never writes to `entities`/`entity_relationships`, and a test greps the source to keep it that way). History is append-only: reversing a decision appends a forward row, so the original answer and its author survive. Routes are analyst+ and org-scoped via `get_current_org_id()`; another org's proposal id hard-404s (a "403 that exists" would confirm the id). A decision emits the `entity_match_proposal_decided` audit event; the scan deliberately does NOT (it can only add or refresh pending questions). `SCANNABLE_ENTITY_TYPES` excludes `person` — two real people share a name far more often than two systems do. Tables `entity_match_proposals` + `entity_match_proposal_history` (DDL in `database/models/entity_match_proposals.py`, migration `0032`, mirrored in `provision.sql`). Frontend: **Entity Matches** (`/entity-matches`, `EntityMatchReviewPage.tsx`, analyst+), whose copy says "recorded", never "merged".
* **2.0-B2 T4 — proposal decisions are durable ACROSS RUNS.** Two additions to the T3 store. (1) `discovery/runner.py` now calls `entity_match_proposals.scan_for_proposals(org_id)` AFTER relationship mapping (tier 3's corroboration reads the observed edges the run just wrote), non-blocking like entity extraction — before T4 the only producer was the manual `POST .../scan`, so no run ever exercised the durability rule. (2) A decision is keyed on the pair's STABLE source identity (`identity_key`), not its entity ROW ids: `proposal_id` hashes row ids, and row ids churn — a connector that starts supplying record ids makes `upsert_source_entity` insert a SECOND resolved row for the same real entity, giving the pair a new `proposal_id` so T3's logic alone asks the answered question again. Per side the identity is `{source_system}|name:{canonical_name}`; the record id is DELIBERATELY excluded because it is the part that churns, and the canonical name is invariant for the pairs this table can hold (only `name_similarity` proposes, and it requires exact canonical-name equality, so the name IS the pair's joint identity and is what the reviewer answered about). `decided_identity_keys()` is the read `record_proposals` consults before writing — confirmed AND rejected both count. Pre-T4 rows self-heal: `backfill_identity_keys()` recomputes the key from the row's own `evidence_payload` (T3 already stored both sides' source system and name), runs on every scan, touches only NULL rows, and leaves a row NULL rather than giving it a wrong key — a wrong key would silently suppress a DIFFERENT pair's question. Schema: `identity_key` + `idx_entity_match_proposals_org_identity`, migration `0033`, mirrored in `provision.sql`.
* `backend/app/entity_unmerge.py` + `finding_reevaluation.py` + `routes_entity_unmerges.py`: 2.0-B2 T5 (AC4) — reversing a resolution. Restoring costs almost nothing because T2's merge never deleted anything: the reversal removes the survivor's claim and the constituent's `merged_into` pointer, leaving identity/edges/status untouched (the row gains `unmerged_from` — HISTORY, not state, since resolution follows `merged_into` only). Three things are load-bearing. (1) **A reversal the next run undoes is not a reversal:** the appliers are idempotent and re-run continuously, and after an unmerge the source cross-reference is still there while a confirmed proposal is still confirmed (T4 made that durable deliberately) — so every unmerge records a BLOCK and `apply_merge` returns the new `OUTCOME_BLOCKED` with a named reason. `blocked` is deliberately distinct from `skipped` ('this applier had no authority' vs 'a person reversed this'); the check lives INSIDE `apply_merge` so every path is covered, reads on the cursor apply_merge already holds (a second pooled connection per merge is a deadlock under load), and applies to EVERY rule — exempting the auto tiers would defeat the reversal on the next run. The block is recorded under TWO keys because the two ways to name a pair fail oppositely: the entity-ROW pair (right when two different entities share a name; breaks on row churn — T4's lesson) and the SOURCE-IDENTITY pair (`source_system`+canonical name; survives churn, breaks on rename). Either matching blocks; if row ids AND a name change together the pair is genuinely new, which is stated rather than hidden. Releasing a block is Owner-only (it re-permits automatic merging of a pair somebody corrected) and deletes nothing. (2) **A chain comes apart at ONE joint:** `A→B→C` is stored FLAT on C's list but the tree survives in the pointers (only the absorbed entity ever has its pointer written), so detaching B hands it back WITH A still merged into it and C loses exactly B's subtree; `detached_subtree` iterates to a fixed point so a child listed before its parent is still found. Such a chain really arises (two entities that are both already survivors, tie-broken on record id then `created_at`), so the contract test builds it through `apply_merge` alone. (3) **Flagging is checkable:** dependents are matched via a finding's OWN entity references (the shapes `llm_enrichment` reads); a finding with NO entity link cannot be shown to depend on the merge, so it is not flagged and IS counted (`unlinkedFindings`) — flagging everything is as useless as flagging nothing, and silently flagging nothing is worse than both. The sweep is bounded to recent runs (references live in run-scoped storage) and REPORTS what it left unread. Flags are keyed `(org_id, opportunity_identity)` — 2.0-A2's lifecycle reasoning: re-evaluation is a property of the PROBLEM, and 'on the next run' is a cross-run question (`opportunity_identity` derives from detector+signal source, never entity row ids, so an unmerge cannot move the key its own flags are filed under). **'Re-evaluated' is a fact:** `materialize_t2` clears a flag via `clear_flags_for_run` on the run that re-observed the finding and records THAT run's id; a finding that stops appearing keeps its flag, clearing touches only `pending` rows, and re-flagging moves the trigger but NOT `flagged_at`. Tables `entity_unmerges` + `finding_reevaluation_flags` (DDL in `database/models/entity_unmerges.py`, migration `0034`, mirrored in `provision.sql`); audit events `entity_unmerged` + `entity_merge_block_released`. Routes are analyst+ except the Owner-only release.
* `backend/app/entity_alias_mappings.py`: 2.0-B2 T1 — the org-configured alias table that tier 2 above auto-merges on. Scoped per `entity_type`; aliases normalise through `entity_resolution.canonical_name_for`; a **conflicting** table (one alias claimed by two groups of a type) is REJECTED rather than resolved by iteration order, which is how a wrong merge ships invisibly. Stored org-scoped in `kv` under `entity_alias_mappings:{org_id}` with `put_alias_mappings` as the only (validating) writer; an invalid STORED table degrades to "tier 2 contributes nothing" with a loud warning rather than breaking a run, while a malformed `ENTITY_ALIAS_MAPPINGS` env override raises.
* `backend/app/routes_entities.py`: `GET /api/runs/{runId}/entities` — analyst+ only. Owns `ensure_entities_table()` (startup-only schema creation).
* `backend/app/context_assembly.py` + `assembly_policy_config.py` + `config/assembly_policy.json`: 2.0-B3 T1 (AC1) — the context assembler's precedence as **declared configuration**. R16-B2 built the assembler with the right discipline (a fixed, documented, deterministic rule sequence) but kept precedence IN CODE: the rank key was a hardcoded `(-confidence, -freshness, id)` and "observed beats inferred" was a boolean switching between two hardcoded orderings — so precedence was untunable, and **source type did not exist as a dimension at all** (a Slack thread and a ServiceNow incident competed on confidence alone, and the more confident chat won). Precedence now lives in `config/assembly_policy.json`; reordering its `ranking` changes composition with no code deploy. **The declaration distinguishes hard tiers from soft preferences**, because collapsing them would quietly weaken R16-B2 AC3: a dimension in `budget_partitions` is a HARD tier (a worse-tier item can never DISPLACE a better-tier item that fit), one in `ranking` is a soft preference within a tier. `origin` is hard by default (observed data must not be displaced by a guess); `source_type` is soft by default so a highly-relevant conversation is not shut out by the mere existence of one structured record — but moving it into `budget_partitions` makes it hard, which is the configurability the AC asks for. **Unknown values sort LAST, never first** (rank derived as `max+1` from the table, so it stays correct as the table grows) — an item earns precedence by declaring what it is, the same fail-safe rule the module already applies to provenance and undated freshness. The loader REFUSES an unknown dimension name (a typo would silently drop a precedence rule), a `ranking` not ending in `candidate_id` (the stable tiebreaker, without which the key is not a total order and determinism is lost), a dimension in both lists, a declared dimension with no rank table, and an out-of-range floor; a missing/invalid file RAISES rather than defaulting, because a deployment that thinks it configured precedence and did not composes findings differently from what its operators believe. `graph_context.py` is the one caller that DEGRADES instead (enrichment is non-blocking) — it falls back to the R16-B2 precedence and logs at ERROR naming the consequence. Every `selection_log` entry now carries `source_type` and `ContextPackage.policy_declaration` records the declaration, because a log read later has to be interpretable against precedence that is now editable. **Additive**: `AssemblyPolicy()` with no declaration behaves exactly as before T1; `AssemblyPolicy.declared()` is the opt-in. Source types (`structured`/`prose`/`code`/`conversation`) match the retrieval substrate's chunk content types plus the graph. **2.0-B3 T2 (AC2) — budgeted composition:** `ContextPackage.budget_report` (surfaced as `GraphContext.budget_report`) answers "did this finding lose context, and to which budget?" — the selection_log always contained it but answering meant parsing every entry, so nobody asked. Shape mirrors MSP-B7's `BudgetReport` (budget/offered/selected/dropped/breached/reason) so the repo has ONE loud-degradation vocabulary. Drops are split by CAUSE (`dropped_by_budget` / `dropped_by_total_budget` / `dropped_below_floor` / `dropped_stale`) because the remedies differ — widen a budget, lower a floor, refresh a stale artifact — and `breached` means a BUDGET cost context, NOT merely that something dropped (a floor/stale exclusion would have happened with unlimited budget, so counting it would send an operator to the wrong lever). **The report is DERIVED from the log**, not counted alongside it, so the two cannot disagree; `offered == selected + dropped` per kind is asserted (an early version subtracted a count twice and reported 2 drops where 5 happened). `caps.total_items` is the per-finding budget across ALL kinds — what actually bounds a prompt, since the per-kind caps sum to 45 — shipped **`null` (disabled) deliberately**: no calibration of prompt size against narrative quality exists and a hand-set number would silently trim every finding, while the per-kind caps keep AC2 exercised in production; `0` is refused. When it binds, BOTH dimensions are deterministic and declared: kinds yield in reverse `kind_precedence` (most substitutable last; graph structure first, because a finding stripped of its entities loses the subject its evidence is about) and within a kind the already-ranked TAIL yields. A trimmed candidate's entry is RE-LABELLED to `total_budget` rather than gaining a second entry — two entries would make the log self-contradictory. **Not wired to 2.0-B1's trace**: `trace_graph.py`/`retrieval_trace.py` are on the unmerged `R2.0_B1`, so the report is shaped for that trace and the wiring left to whichever merges second. See `docs/assembly_policy.md`.
* `backend/app/mode_parity.py`: 2.0-B3 T6 (AC6) — **AI-mode parity for context assembly**. Assembly must behave identically across the three AI modes (`hosted`/`in_boundary`/`customer_tenant`) except for model quality, and where a mode can't support a step the finding degrades with a VISIBLE label (the 1.9 pattern, mirroring `discovery/packs/security_ops_ai_mode.py`'s `HOSTED_NARRATIVE_LABEL`). **Parity holds BY CONSTRUCTION**: `context_assembly.assemble_context` makes no model call (a T6 test AST-asserts it imports no gateway), so the same seeded `(graph, policy, evidence)` yields a byte-identical `ContextPackage` in every mode — the mode can only affect what the `evidence_source` proposes, never an assembly decision. **The one step a mode STRUCTURALLY can't support is evidence retrieval**, which needs embeddings: the hosted provider has no embeddings endpoint (`HostedModelProvider.embed` returns `[]`), so in hosted EMBEDDING mode retrieval is inert — previously loud at startup (`model_gateway.validate_provider_config`) but SILENT on the finding. This module makes it visible: `assembly_mode_report()`/`mode_degradations()` report each unsupported step with a verbatim `RETRIEVAL_UNAVAILABLE_LABEL`, keyed on the EMBEDDING mode (resolved independently of generation), and `graph_context.build_graph_context` now stamps them onto `GraphContext.mode_degradations` (additive; empty in an embedding-capable mode, so those findings are byte-identical to pre-T6). Narrative-generation degradation is NOT modelled here — all modes can generate and a runtime generation failure is already labelled `llmGenerated=False` on the enrichment result. PURE and fail-SAFE like the SecOps gate: reads only provider NAMES (no network), and a resolution failure resolves to `hosted` (the most-degraded reading) so a misconfiguration can never hide a degradation. Contract test: `tests/contract/test_r2_0_b3_t6_mode_parity.py`.
* `backend/app/narrative_discipline.py`: 2.0-B3 T4 (AC4) — **narrative discipline enforcement**: every ASSERTED CLAIM in an assembled narrative must trace back to supporting evidence, and a claim that does not is a build failure. The unit of assertion is the why-bullet (`aiWhyBullets`); each carries the `[OBSERVED]` / `[INFERRED: <basis>]` provenance tag the grounded prompt already stamps (`llm_enrichment.build_grounded_opp_prompt`), and **that tag IS the claim's declared link to evidence**, so it is what the checker holds to account. A claim resolves against a `SupportIndex` built from the assembly's OWN output — the selected entities/relationships/evidence of the `ContextPackage` plus the finding's `evidenceIds`/`grounding_evidence_ids` — never an ambient corpus: an `[OBSERVED]` claim must REFERENCE the support (name a selected entity or cite an evidence id) and the package must actually hold observed evidence; an `[INFERRED: <basis>]` claim's named basis is its link, so an empty basis is unsupported connective language; an untagged or `[UNVERIFIED]` claim declares no link at all and fails. The forward-looking structured form `{"text":…, "evidenceIds":[…]}` (what 2.0-B1's trace will carry) resolves iff every cited id is in the support set — so **B1's trace is the RENDERER of the same claim→evidence linkage this module ENFORCES** (B1 is deliberately not on this branch, per `graph_context.py`). Four detectors ship: `pack_version_change` (a field comparison, nearly free, and disproportionately important — a pack version bumps whenever detector/scorer/corroboration logic changes, so movement across a boundary may reflect a threshold edit; a missing version is an *advisory*, since absence of information is not evidence of change), `volume_shift`, `ci_population_change` (compares the resolved entity set via the shared `ENTITIES_VISIBLE_AS_OF_RUN_FROM_WHERE` clause, keyed on `entity_type:canonical_name` not the random per-row uuid; a 2.0-B2 merge/unmerge surfaces here as a caveat rather than looking like organic drift; a tiny estate uses an absolute-count rule because a fraction is meaningless at n=3), and `seasonality_window_mismatch`. **Caveats are structured data** (`type`/`severity`/`detail`/`detectedAt` + `thresholdBasis`), never prose, so T6 counts them and B1 renders them; `summarise_confounders` travels with the record and the counts are promoted to columns (migration `0034`). **Thresholds are configuration, not constants** — in `config/outcome_confounders.json`, each declaring `basis` as `measured`/`operationally_justified`/`provisional` (volume-shift and CI-population are honestly marked provisional), and the seasonality WINDOW DEFINITION is configurable (`calendar_month_overlap`/`fiscal_quarter`/`declared_periods`/`disabled`) because a hardcoded calendar is wrong for much of the customer base. **New confounder types are registerable** via `register_confounder_detector` — a test asserts the movement engine names none of the type codes, so adding one never requires editing the comparison engine.
* `backend/app/opportunity_movement_record.py` + `opportunity_movement.py` + `routes_opportunity_movement.py`: 2.0-A2 T3 — post-action monitoring: re-measure the signals a T2 baseline froze and store the comparison (AC2/AC5/AC7). **Three gates, all required before a measurement exists**: the lifecycle state must be one a recorded action put it in (`is_measurable`), a frozen baseline must exist, and a run must have landed STRICTLY AFTER the action date. * `backend/app/run_reproducibility.py`: 2.0-D4 T3 — the **per-run version record** (AC4), answering the question nobody asks until six months later: "today's run of apparently the same data produces different findings; what changed?". The bar is stated in the module and is **explanation, not byte-identical replay** — replay re-serves persisted artifacts and does not re-run ingestion or regenerate LLM output, and this does not change that. `diff_reproducibility` is the actual deliverable: a two-run comparison naming which of the four dimensions differs, with a readable one-sentence summary (the shape a customer will want in the UI). **Packs are READ, not rebuilt** — `materialize_t2` already stamps `packIds`/`packVersions`/`packs`, and recomputing here would create a second source of truth that could disagree with the findings' own stamps; a test verifies every registered pack declares a semver version rather than assuming the 1.9 bump-discipline holds. **AI mode records BOTH providers** (`resolve_provider_names`, added to the gateway so this module never reads the env vars itself) because they resolve independently and the shipped config deliberately mixes them — one collapsed field would be wrong for the default deployment — plus the R18-B1 `(embedding_model, embedding_model_version)` identity. **Connector "version" needed a definition first**: a SaaS connector has none in the sense a pack does, so the record carries the three things that actually vary — the negotiated `api_version`, the `auth_mode`, and a `code_fingerprint` derived from the ingestor SOURCE rather than a hand-maintained string. That is deliberate: **a version that never changes is worse than an absent field because it invites false confidence**, and a source fingerprint cannot go stale (the trade-off — a comment-only edit also moves it — errs in the useful direction). Two quiet-wrong-answer bugs were found and fixed while building it: connectors do not agree on the version constant's NAME (`API_VERSION` vs `JIRA_API_VERSION` vs `SN_API_VERSION`), so ServiceNow and Jira initially reported no version at all — `_API_VERSION_ATTRS` now enumerates them and a test fails the build if `discovery/ingest/` introduces a name that is not listed; and the Azure connector pins one api-version per ARM surface in SIBLING client modules, so reading only `azure_events.py` reported null where the platform demonstrably does pin versions (`CONNECTOR_VERSION_MODULES`). **Assembly policy is honest about what does not exist**: 2.0-B3 has not landed and `AssemblyPolicy` declares no version, so `version` is `None` with the reason recorded IN the record (the 2.0-A1 posture) rather than a placeholder — but the EFFECTIVE policy values plus a fingerprint are captured, since those are what actually change behaviour, and a test detects B3 landing so the 'not landed' reason cannot go stale. Stamped onto the run as `run["reproducibility"]` inside a try/except (structurally asserted): a version record explains a run and must never be the reason one fails.
* `backend/app/export_signing.py` + `audit_export.py` + `routes_audit_export.py` + `docs/audit_export_and_retention.md`: 2.0-D4 T2 — the **signed, period-scoped audit export** (AC2/AC3). Turns the audit trail from something the platform HAS into something a customer can hand an auditor. The only prior read surface was run-scoped `GET /api/runs/{runId}/audit`, which cannot answer "every state-changing action in this org between these dates, and prove this file is what the system produced". So the export differs in three ways: a PERIOD not a run (a plain `to` date covers the whole day — the reading an auditor assumes and a naive implementation gets wrong); **org scoping in the SQL** (`WHERE org_id = %s`, the A2/A3 store pattern — isolation asserted after retrieval is not isolation, and the request body deliberately has NO `org_id` field); and a signature over the exported bytes. **`export_signing.py` is SHARED on purpose** — 2.0-B1's evidence bundle needs the identical "altering any byte fails verification" property, and a platform with two signature schemes has a weakest one. Ed25519 reused from `licensing.py`, not re-chosen: with an HMAC any signature the customer can verify the vendor could also have forged, so the auditor would be trusting CloudFulcrum rather than verifying the DEPLOYMENT. **Keys are separate from licences, deliberately**: licence signing is a VENDOR capability (private key in AWS, never in a customer install) while export signing is a DEPLOYMENT capability (`AUDIT_EXPORT_SIGNING_KEY` / `AUDIT_EXPORT_PUBLIC_KEY`) — one shared key would either put licence-minting power in every deployment or make every export a vendor attestation. No fallback: an unconfigured deployment gets 503, never an unsigned artifact that looks signed. The signature covers the PAYLOAD only, never the envelope, so verification never has to strip its own signature back out; `content_sha256` is diagnostic only (a tamperer can recompute it — it distinguishes "truncated in transit" from "deliberately rewritten"), and `SIGNATURE_VERSION` is checked so a signature made under a different rule can never verify under this one. `MAX_EXPORT_ROWS` caps a disclosure and reports `complete: false` + `truncated` rather than handing over a partial trail as a whole one. **Exporting is itself audited** (`AUDIT_EXPORT_GENERATED`) because it is a DISCLOSURE even though it mutates nothing — genuinely recursive, so a later export shows who read the trail before; the row is written BEFORE the payload is built (so a failed serialisation cannot lose the record), which is why an export never contains its own generation row. A refused export is audited too, with `outcome: failure`. The route is a POST specifically so T1's conformance sweep enumerates it and the recursion is ENFORCED in CI rather than merely implemented.
* `backend/app/middleware/audit.py`: audit trail — `log_event` is the single write point into `audit_log`, attribution goes through the shared `resolve_event_org_id` so an unattributed event is marked UNATTRIBUTED rather than filed under the real `default` tenant, and the table is INSERT-only. **2.0-D4 T1 made the vocabulary GOVERNED rather than incidental**: `AUDIT_EVENT_REGISTRY` was documentation (`log_event` accepted any string, while `telemetry.record_event` genuinely raises), so a typo wrote a row that no registry-filtered query would ever return — the row existed and the trail still had a hole. `log_event` now raises `UnregisteredAuditEvent` for an unlisted type. * `backend/discovery/concepts/` (`model.py` + `contracts.py` + `conformance.py`): 2.0-B4 T1 (AC1) — the **normalised concept set**, widening MSP-B0's one-model-per-source-family pattern from cloud events to business workflow, documents, conversations and code. Seven concepts: `work_item`, `actor_group`, `artifact`, `state_transition`, `approval`, `assignment`, `entity_reference`. **Six are `CommonSignal` profiles; `entity_reference` is a VALUE TYPE** — it has no observation of its own (it is always carried by one), so making it a signal would force every construction to invent a provenance spine, which R16-B1 forbids; B0's `ResourceRef` plays exactly this role. `OperationalEvent` remains a SIBLING profile, not a parent — as a base class every cloud connector would have inherited workflow fields meaning nothing to it. **Closed vocabularies validated at construction** (B0's rule) so an unmapped native value fails at the connector, not in a finding; `STATUS_CATEGORIES` is deliberately COARSE with the source's value kept on `native_status`, and two distinctions carry weight — `cancelled` is NOT `resolved` (treating abandoned work as completed overstates throughput) and `reopen` is NOT `status_change` (rework is the signal; collapsing it erases it). **Groups, never individuals**: `ActorGroup` is the only actor concept, no value denotes a person, `member_count` is an aggregate with no roster at any version, and every group-bearing field is an `EntityReference` rather than a string so a mapper cannot put a name there. * `backend/discovery/ingest/aws_watermark.py`: MSP-B1 per-scope time positions for the AWS poll source — the resume-correctness core for the two time-series surfaces. `TimePosition` + `encode_position`/`decode_position`/`watermark_of`/`advance_ascending`/`advance_descending`. Two properties it exists to guarantee. (1) **No truncation loss**: CloudWatch is read `ScanBy='TimestampAscending'` so a page-budget cut-off is a complete PREFIX and the watermark can safely advance; CloudTrail is newest-first with no sort control, so while truncated the watermark is PINNED and a `ceiling` walks backwards through the older remainder (`pending_high` holds the eventual watermark until the window drains), with `PollPage.has_more` driving the continuation. Advancing past an unread backlog — the original behaviour — stranded those events permanently. **Only a genuinely drained window promotes `pending_high`**: a truncated read that yields nothing this position accepts (routine — CloudTrail delivery is eventually consistent and the management-event filter drops records) PINS the position and retries next run, because treating an unreadable page as a drained one closes the window over a backlog that was never read. For the same reason a same-instant ceiling is not automatically "no progress": newly-read ids AT that instant are carried forward into `ceiling_ids` (the mirror of `advance_ascending`'s same-instant merge) so the next poll excludes them and the walk continues; the walk pins, loudly, only when the instant yields nothing new. (2) **No boundary drops**: comparison is on PARSED instants (a boto3 `datetime`, `…Z`, and `…+00:00` are the same instant; string comparison said otherwise), and the position carries the provider event ids seen AT the watermark instant so a late-arriving same-second event is admitted while already-seen ones are not re-read (CloudTrail has second granularity and eventually-consistent delivery, so this is routine, not hypothetical). The descending walk is additionally bounded in DEPTH by `advance_descending(..., max_backfill_seconds=…)` — measured from the backfill's own `pending_high`, so it is independent of when the run happens; on reaching it the window CLOSES (promote `pending_high`, clear the ceiling) and logs at WARNING, because an unbounded initial walk of the 90-day `LookupEvents` retention pins the watermark across many runs and delays every new event behind the whole history. Events older than the depth are consequently not ingested — a declared, configurable initial-load boundary (`AWS_EVENT_MAX_BACKFILL_DAYS`), never a silent thinning. Wire format is backward-compatible: a position with nothing extra to carry encodes as the **plain ISO string** it always was. The checkpoint value stays opaque to the runner (R16-A1 AC5) — read it with `watermark_of`, never by comparing the raw string.

All three V1 streams share ONE per-subscription poll/checkpoint engine (`_ingest_stream`): each polls every PINNED subscription independently with its OWN checkpoint, keeps only records strictly newer than that checkpoint (`_filter_new`/`_max_ts` on ISO timestamps — no re-reads), normalises each through its B0 mapper (`map_azure_monitor` / `map_azure_activity_log` / `map_service_health`), and emits a transport record carrying the subscription as `account_scope` on the WRAPPER (never a connector-invented detector field). **The two shared-skeleton (MSP-B1/AT-641) contracts are implemented natively here** — the connector predates `CloudEventConnector` and still rides `ChangeBasedIngestor`, but must not diverge from the AWS path: (1) **transport re-stamp (AC4)** — `_stamp_transport` sets each mapped event's `source_system` to the provider family `'azure'` and re-points its OBSERVED pointer at the native cloud artifact (raw payload stored under the same `(org, 'azure', signal_id)` tuple the pointer carries), while the mapper's `event_signature` is left UNTOUCHED — `OperationalEvent` derives the signature only when the field is empty, so the re-stamp provably cannot overwrite it, which is what keeps a native event equal to its bridged twin in every field but that one; the mapper's per-stream B0 source system (`azure_monitor`/`azure_activity`/`azure_service_health`) stays on the record wrapper as `surface` (and in `artifact_id`), so nothing is lost. (2) **MSP-B7 admission** — the connector owns its OWN `OpsEventStream` and admits every event inside `_ingest_stream` (exposing `active_signals()`/`budget_report()`, the AWS read side), so no caller can consume its events un-deduplicated: re-fires fold with a count, an exact redelivery is dropped rather than re-emitted, `has_capacity()` is checked BETWEEN subscriptions so the budget stops the *fetching* not just the admitting, and a mid-page deferral leaves that subscription's checkpoint UNADVANCED (`status='deferred'` + named reason) so the remainder is re-polled next run instead of lost. `build_ingestor` resolves `CALIBRATED_RUN_EVENT_BUDGET` exactly as the AWS one does, so the runner path is budgeted on both clouds while a directly-constructed test ingestor stays unbounded; `runner._ingest_azure_events` merges the budget report into the `azureEvents` health block and degrades the reported status when it is breached. A subscription's checkpoint advances ONLY after it processes cleanly; a per-subscription fetch failure is caught, reported loudly in `subscription_status`, and leaves that subscription's checkpoint unadvanced while the others continue (no silent thinning); a single malformed record is loud-skipped. SCOPE DEFENCE: the Activity Log stream ingests `category='Administrative'` ONLY (`azure_admin_events.is_administrative` drops ServiceHealth/Security/Policy/… — T3-AC4); Alerts/Activity Log/Service Health are the ONLY three classes (no metrics/Log Analytics/diagnostic logs/Defender/Sentinel). `ingest_all` polls all three (one shared ARM token; namespaced opaque checkpoint `{stream: {sub: iso}}` via `encode/decode_stream_checkpoints`, back-compatible with the T2 flat alerts map); `ingest_changes` is the pipeline entrypoint over `ingest_all`. T6 (AT-653) adds RESILIENCE inside the same engine: `_fetch_with_retry` retries ONLY transient failures (`classify_failure` → throttled/5xx/timeout/network) with bounded exponential backoff (`RetryPolicy`, env-tunable `AZURE_EVENT_MAX_RETRIES`/`_BACKOFF_*`, injectable `sleep_fn`) — auth/authorization/not-found/malformed are never retried; every failed subscription is reported loudly into run health via the `ingestion.subscription_health` telemetry event (category/retryable/attempts/recoverable, secret-free) with its checkpoint left unadvanced (no silent thinning), while healthy subscriptions continue; a connector-level auth failure is caught by `ingest_all` and reported for every pinned subscription (checkpoints preserved), never crashing the run. `azure_alerts.py` / `azure_admin_events.py` own the injectable clients (Fixture offline / Http live outbound-only GET). Auth REUSES the existing Azure AD plumbing — `AzureEventIngestor.acquire_token` resolves a per-org service principal from the vault (`app.auth.vault` static-credential machinery: username=client_id, secret=client_secret, base_url=tenant_id — no new vault path) and mints an ARM-scoped token via the SHARED client-credentials exchange `app.auth.oauth.request_client_credentials_token` (extracted from `get_client_credentials_token` so there is ONE token-exchange implementation, not a second copy for the vault path). Environment-aware from day one via the SINGLE shared map `app/azure_environments.py` (MSP-B2 T4 / AT-651 — `azure_events_config` re-exports it, no duplicate endpoint map): `AzureCloud` → login.microsoftonline.com / management.azure.com, `AzureUSGovernment` → login.microsoftonline.us / management.usgovcloudapi.net; `resolve_environment(name)` is config-driven (default AzureCloud, unknown → error), ARM scope is `{resource_manager}/.default`. That shared module is dependency-free/credential-free and is the one Azure environment source any Azure integration reuses (this connector now; the model gateway's Azure OpenAI Government surface per B9). Both access modes work — Lighthouse (one SP/home tenant, many delegated subscriptions) and direct (per-tenant SP); the token is minted against the SP's home tenant either way. SUBSCRIPTION DISCIPLINE (AC4/AC7): the pinned `subscriptions` set in config is the ONLY set ingested — `authorized_subscriptions()` never includes an unpinned delegated subscription, `newly_delegated()`/`pending_delegated_subscriptions()` report delegated-but-unpinned candidates for Owner approval without ingesting them, so the connected estate never auto-grows. Config is non-secret (offline `fixtures/azure_events_config_sample.json`; live `AZURE_EVENT_CONFIG` JSON, org-keyed or flat); an inline secret is rejected via the shared `operational_config.find_inline_secret_keys` guard. The connector is transport-only (no detector fields) and does no module-level `app` import (offline-safe). **2.0-D3 T1** layers the bounded Application Insights read scope on top (see `azure_app_insights.py` below): `_ingest_stream` gained a `scope_of` hook (alerts + service health pass one) and an exclusion gate that runs BEFORE the incremental filter, so an excluded record cannot advance a checkpoint either; `subscription_status` gained `app_insights` / `telemetry_excluded` counts (both omitted when zero, so a pre-D3 status shape is byte-identical), and `runner._ingest_azure_events` derives an `app_insights` run-health sub-block (records / components / `by_signal_kind`) from the emitted records — omitted entirely when the poll met no App Insights signal.
* `backend/discovery/signals/app_insights_signal.py`: 2.0-D3 **the single source of truth for the Application Insights signal vocabulary** — which records are App Insights operational signals, which of the four kinds each is (`availability` / `application_failure` / `dependency_failure` / `health_transition`), and which are excluded telemetry. Pure: no I/O, no clients, no `app` import, no ARM knowledge. It lives in `signals/` rather than `ingest/` because TWO consumers on opposite sides of the ingest boundary need identical answers — the T1 bounded read scope (`ingest/azure_app_insights.py`, which re-exports every name from here) and the T2 B0 mapper (`signals/reference_mappers.map_app_insights`, which must derive the application and kind from the raw record alone, since a mapper is invoked standalone by the golden-fixture harness). A second copy in the mapper would be exactly the drift this repo was already bitten by (three copies of the CI-dependency traversal, which had silently diverged), and having the mapper import from `ingest` would invert the layering (`ingest` modules import `signals.reference_mappers`, so the reverse edge risks an import cycle). `test_app_insights_mapper.py::TestSingleImplementation` pins that both modules resolve to the SAME function objects AND that the ingest module defines nothing but its three transport guards — so a re-introduced private copy fails the build. Also owns `is_alert_condition_active` (active-vs-resolved read from Azure's own `monitorCondition`; an ABSENT value reads as ACTIVE, because an alert that does not say it is resolved is the firing and treating it as resolved would silently downgrade a live failure), `APP_INSIGHTS_EVENT_TYPES` (the provider-native `ApplicationInsights/<Signal>` tokens) and `app_insights_event_type()`.
* `backend/discovery/signals/reference_mappers.py` → **`map_app_insights`** (2.0-D3 T2): the B0 mapper. Accepts a record from EITHER D3 surface and resolves which from the record's own shape (`detect_surface`), so it stays standalone-invocable like every other reference mapper. Four things it gets right on purpose. (1) **Resource = the monitored application, never the alert rule** — the explicitly-supplied monitored-application reference when Azure gives one (`MONITORED_APPLICATION_FIELDS`), else the App Insights component; both explicit, nothing inferred. `resource_type` comes from the SAME shared `azure_resource_type_from_id` table every other Azure mapper uses (a `components` id → `monitoring`, an App Service id → `compute`); D3 deliberately adds no per-surface override, because a provider-specific carve-out in shared code is how that table stops being shared — and nothing downstream branches on `resource_type` (verified: only `cloud_ops_runtime.py:359` carries it as metadata). (2) **`event_class` maps D3's "alarm/health" wording onto B0's CLOSED vocabulary**: health transition → `state_change`; ACTIVE availability/application/dependency failure → `error`; a RESOLVED failure or an unclassifiable in-scope alert → `state_change`. Consequence stated rather than hidden: a firing and its resolution carry different classes and therefore different signatures — intended, since they are different operational facts, and it is what lets recurrence count firings without resolutions diluting the count. (3) **`event_type` is where the App Insights signal survives** the class collapsing to two tokens, so availability / application-failure / dependency-failure / health stay distinguishable. It is the KIND, not the customer's rule name, because two rules both reporting "availability of app X is failing" are ONE recurring operational fact and folding them is what stops MSP-B7 counting the same problem twice. **The one exception is deliberate**: an UNCLASSIFIABLE in-scope signal appends the rule name (`ApplicationInsights/Signal/<rule>`), because folding two unknown conditions would be an unjustified claim — the signature service guarantees genuinely different events get different signatures, and we cannot know two unknowns are the same fact. Both directions are pinned by tests. (4) **The signature comes from the shared service**, never computed here (a structural test asserts the mapper never calls `compute_event_signature` itself); `azure_app_insights` is registered in `event_signature._SOURCE_SYSTEM_FAMILY` → `azure`, without which the same fault would fingerprint differently depending on which Azure surface reported it. The payload is BOUNDED and curated (the complete Azure record lives only in the AT-638 raw-event store, reachable via the event's OBSERVED pointer) and deliberately introduces no `principal`/`actor`/`user`/`caller` key, since one of those would silently change what the fingerprint keys on. Golden fixtures pinning the ENTIRE normalised output for every supported event type: `discovery/tests/fixtures/app_insights_mapping_golden.json` (expectations hand-written from the spec, not dumped from the implementation, and the signature validated by RECOMPUTING it from stored components rather than pinning a hash). Documented in `docs/msp_operational_event_schema.md` §5.
* **2.0-D3 T4 — Application Insights volume discipline.** App Insights adds NO volume-management code: its events ride the four MSP-B7 disciplines exactly as every other cloud source does (dedup via the connector's own `OpsEventStream`, the shared `apply_noise_floors`, the shared `CALIBRATED_RUN_EVENT_BUDGET`, and the shared `join_within_window`/`gate_operational_corroboration`), and structural tests over `ops_stream.py`/`noise_floor.py`/`budget.py`/`aggregation.py`/`ops_calibration.py`/`correlation/windows.py` assert none of them grew an App Insights branch. Class mapping matters for floors: an ACTIVE failure is `error` — a PROTECTED class absent from the floor map, so never suppressed — while a health transition is `state_change` and takes the shared floor, suppression always counted and reported. T4 fixed two REPORTING holes, both about not overstating a clean run. (1) `AzureEventIngestor.deferral_report()`: the B7 budget counts deferred EVENTS, which it can only do for events it saw, so when capacity is exhausted and the connector correctly stops REQUESTING further pages those polls contribute no count and `BudgetReport.breached` stays False — a run that skipped whole subscriptions reported a clean budget. The report names every cut-short `(stream, subscription)` and `complete` goes False; `runner._ingest_azure_events` merges it as `health['deferrals']` and degrades the status, mirroring the AWS `poll` block. (2) `cloud_ops_runtime`'s event-signature `transport` field read `event_history_bridge` UNCONDITIONALLY, which was already false for every natively-ingested Azure and AWS event (three producers feed that assembly) and would now also mislabel every App Insights signal; it is derived per folded firing from each member's evidence pointer, exposed as a `transports` list with the scalar reading `mixed` rather than silently picking one. Note an exact bridged twin shares its provider event id and is deduped as a redelivery, so `mixed` arises only when two DISTINCT firings of one condition arrive by different routes. Documented in `docs/msp_operational_event_schema.md`; suite is `discovery/tests/test_app_insights_volume_discipline.py`.
* `backend/discovery/ingest/app_insights_association.py`: 2.0-D3 T3 — **IIS / .NET / CMDB association, by EXPLICIT reference only**. Answers "which application component or configuration item is affected by this App Insights alert?", and is defined as much by what it refuses as by what it does. The ONLY inputs are stable identifiers a human already committed to: `DotNetAppTarget.app_id` (resolved against the existing `dotnet_app_config.load_targets` set, so an association can only point at an application the customer already declared — an id outside that set is a typo, not an association) and the ServiceNow `sys_id` (resolved through the existing conservative, read-only, org-scoped `app.entity_resolution.lookup_resolved_entity` against `entity_type='system'` / `source_system='servicenow'`, which is exactly the shape MSP-B3's CMDB ingestion writes). **The single most important line in the module is what it does NOT pass**: `lookup_resolved_entity` falls back to canonical-NAME matching when a `source_record_id` finds nothing, so the CMDB lookup passes **no `display_name`** — otherwise the forbidden name-based association would arrive through the back door. A test pins that we never pass one. Nothing is ever matched on a name, URL, hostname, IIS site name, resource group, owner, environment, tag, or events at similar times; "Orders API" existing in both systems is not evidence, and a parametrised test seeds each of those soft signals and asserts nothing associates. **Everything ambiguous stays unassociated with a NAMED reason** (`duplicate_configuration` / `no_target_declared` / `dotnet_app_id_not_configured` / `cmdb_sys_id_not_resolved` / `cross_organization_reference`) so an operator can see why their config did not take effect: a component with MORE THAN ONE config entry is refused outright **even when the entries agree**, because a config naming one component twice is ambiguous about intent; an entry naming another org is refused; and a returned CI whose own `org_id` differs is refused as belt-and-braces on top of the org-scoped lookup. Matching on `app_id` is EXACT (case, separators and prefixes all matter) — only surrounding whitespace is trimmed, which is config hygiene, not matching; ARM component ids fold case because Azure resource ids are case-insensitive, which is identity rather than fuzziness. Config is bounded and non-secret (`APP_INSIGHTS_ASSOCIATIONS` live / `fixtures/app_insights_associations_sample.json` offline; org-keyed object with a `default`/`*` fallback OR a plain array, the `ENTERPRISE_APP_REPOS` shape), an inline credential-shaped field is REJECTED via the shared `operational_config.find_inline_secret_keys` guard, and the offline fixture deliberately names the app_ids the offline .NET fixture actually configures so a shipped default demonstrates a resolved association rather than training operators to ignore a permanently-unresolved field. **The result rides the record WRAPPER, nested inside the existing `app_insights` block — never the MSP-B0 event**: the event's identity, its deterministic `event_signature` and its transport equivalence must not depend on whether a customer happens to have configured an association, and a test asserts the event is byte-identical with and without one. An otherwise valid event always ingests; a resolver that raises is logged and degrades to no association, never a failed poll.
* `backend/discovery/ingest/azure_app_insights.py`: 2.0-D3 T1 — the **bounded Application Insights read scope**. Deliberately NOT a connector: it adds no client, no credential type, no ARM surface and no endpoint, because the story's constraint is "App Insights alerts and health/failure events **via Azure Monitor surfaces already reached by B2**" — adding a surface here would be the "new connector family" D3 rules out. It applies a scope decision to records `azure_events.py` already fetches from Alerts Management and `Microsoft.ResourceHealth/events`. **2.0-D3 T2 moved the classification RULES to `signals/app_insights_signal.py`** (see above) and this module re-exports them, so what remains genuinely its own is the transport-level trio: `ALLOWED_ARM_PATHS`, `EXCLUDED_ENDPOINT_MARKERS` + `assert_read_allowed`, and `AppInsightsScopeViolation`. The rules it applies decide two things: (1) **is this in App Insights scope?** — only on an EXPLICIT `/providers/microsoft.insights/components/<name>` reference read from documented reference fields only (`alertTargetIDs`/`alertId`; `properties.impactedResources[].resourceId`/`resourceId`/`resourceUri`); there is no name matching or resource-group heuristic, and a different `microsoft.insights/*` type (metricalerts, actiongroups, webtests) is never mistaken for a monitored application. A `None` scope changes nothing, so D3 never re-classifies, narrows, or drops a B2 record. (2) **which of the four signal kinds is it?** — `availability` / `application_failure` / `dependency_failure` / `health_transition` (closed vocabulary), decided from the alert's DECLARED fields only (rule name, signal type, monitoring service, description, condition type, metric name) — never from telemetry content, since telemetry is not read at all. Classification **precedence is fixed and tested** (availability → dependency → application failure) because a dependency-failure alert is also a "failure" and an availability alert usually says "failure" too, so without an order the same alert could land in two kinds; an in-scope record whose kind cannot be established keeps `signal_kind=None` rather than being forced into a bucket (the same "ambiguous stays unresolved" rule D3's AC3 applies to IIS association). **Exclusion is enforced twice, because a comment is not a control**: `is_excluded_telemetry` recognises telemetry/analytics record SHAPES (App Insights envelopes via `itemType`/`baseType`/`Microsoft.ApplicationInsights.*`, KQL `tables`+`rows` results, metric series) so seeded telemetry is dropped loudly and counted instead of ingested — it is conservative by construction, short-circuiting on the alert/activity/health envelopes FIRST so it can never swallow a record B2 legitimately ingests, and an UNRECOGNISED record is not excluded (the gate keeps known telemetry out; it is not an allow-list that would silently narrow B2); and `assert_read_allowed(url)` raises `AppInsightsScopeViolation` for an excluded surface, wired into BOTH live clients (`azure_alerts.HttpAzureAlertsClient`, `azure_admin_events._HttpStreamClient`) so the boundary holds even for a caller that never hands us a record. `ALLOWED_ARM_PATHS` is an EXPLICIT enumeration of the three paths D3 permits, and `test_azure_app_insights_scope.py` walks the AST of every `azure_*.py` in the ingest layer asserting each ARM path constant is in that set — so adding a metrics / Log Analytics / App Insights REST read fails the build with no test edit. The scope rides the record WRAPPER as `app_insights` (never the event), so no provider-specific detector field is invented; turning it into event-level normalisation (resource = the monitored application, class = alarm/health) is D3 T2's B0 mapper, and associating the application with a `dotnet_app*` component or CMDB CI is T3. Fixtures: `fixtures/azure_app_insights_sample.json` carries the four positive kinds, two deliberately out-of-scope B2 records, an unclassifiable in-scope case, and the negative set (metrics, raw requests, traces, page views, exceptions, KQL results, SUCCESSFUL dependency telemetry) — the last of these is the point that a dependency-failure ALERT is in scope while individual dependency CALLS are telemetry.

* `backend/discovery/ingest/git_content.py`: R18-A2 Git **content** change-based ingestor (`GitContentIngestor`, `connector_id='git_content'`) — reads repository file content into the retrieval substrate. Distinct from the GitHub *signal* connector (`connectors/saas/github.py`), which reads activity metadata only. The commit graph IS the change feed: the opaque checkpoint is the last-ingested commit SHA per repo (a per-repo cursor map; a plain SHA once synced, `{sha,offset}` while a first load streams so it resumes), a first run streams the HEAD tree as resumable checkpointed batches, and incremental runs process only the files `since..HEAD` touched. Per-repo **include/exclude path filtering** (AT-530, `PathFilter` / `DEFAULT_EXCLUDE_GLOBS`) drops vendored deps / generated-build output / dependency lockfiles by default (applied to BOTH the first-load tree and the incremental diff); the defaults are editable per org (`path_defaults` in the config source / `GIT_CONTENT_PATH_DEFAULTS`) and per repo (`include` allow-list, `exclude` globs, `use_default_excludes` toggle). **Deletion propagation** (AT-533, AC3): a file removed by a commit is yielded as a `change_kind='deleted'` record (so the runner emits a deleted event) AND routed in the same batch to `retrieval.ingest.remove_content`, so its chunks leave retrieval and it stops being retrievable (idempotent, org-scoped; excluded paths are never routed). **Secret redaction** (AT-531, AC5): `_secret_scan` runs unconditionally between extraction and every `ingest_content` hand-off — for BOTH the file stream and the commit corpus — redacting key/token/password signatures (via `discovery/ingest/secret_redaction.py`) so a committed credential is never indexed into a retrievable store ("redact before index, always"). Each redaction is recorded as an `ingestion.secret_redacted` telemetry event + a WARNING (pattern types + counts only, never the value) for run-health visibility. Offline reads `fixtures/git_content_sample.json`; live shells out to `git` in a local clone declared per deployment via `GIT_CONTENT_REPOS`.

* `backend/discovery/projection/`: 2.0-A1 per-opportunity **intervention projection** — what changes if the agent is built. A projection is a DIRECTION and a MAGNITUDE BAND on measured signals, never a point estimate and never a savings claim. `signal_registry.py` maps each detector to the real measured field names it already emits (the projection never invents a signal). `model.py` decides direction, horizon, the replaced manual step, the movement signal, the assumption ledger, and the computation basis — it does NOT compute a width. `band_width.py` (T4) owns band width end to end: a deterministic function of exactly FOUR evidence inputs (sample size, recurrence stability, corroboration status, confidence cap status) with fixed weights summing to 1.0, plus the projection-strength scalar and the AC4 ordering rule. **Width is never a hand-set number** — there is deliberately no env var, no config entry, and no override parameter, and a structural test fails the build if `band_width.py` ever reads the environment. Thinner evidence strictly widens; stronger corroboration strictly narrows. A capped (single-source) finding is widened on TWO axes, labelled, its strength clamped to `CAPPED_STRENGTH_CEILING`, and structurally demoted by `projection_rank_key` so it can never out-rank a corroborated equivalent on strength alone. Pure and deterministic (no DB, no `app` import, no clock, no LLM) so a stored projection compares byte-for-byte with a recomputed one — that is what 2.0-A2 validates a measured outcome against. Rules documented in `docs/projection_band_width.md`; bump `BAND_WIDTH_MODEL_VERSION` (and `PROJECTION_SCHEMA_VERSION` when stored bands stop being comparable) on any change that moves a band for unchanged evidence. `recommendation.py` (T5) composes the customer-facing recommendation in INTERVENTION language — always five parts (what the agent handles / which recurring cases are in scope / what remains manual / which measured signal should move / band and horizon) — and rides ON the projection payload, so every surface renders the SAME wording and none composes its own. `vocabulary.py` (T5) is the AC3 template-level guard and the single source of truth for what AgentIQ may never say about a projection: guarantee language (`will reduce`, `guarantees`, the whole `eliminat*` family, `ensures`, `savings`, `ROI`) and point-estimate savings claims (`reduce cost by 40%`, `40% reduction`, `12 hours saved`). It deliberately does NOT flag magnitude bands (ranges are masked before the point-estimate rules run), measured observations, or machine identifiers — a guard that flags the evidence trains people to ignore it. Enforced at every boundary, not just in tests: `assert_clean` at recommendation build time (our own templates must be clean by construction), `_scrub_enrichment_result` on LLM output in `llm_enrichment.py` (closing the Sprint-5 "post-generation validation deferred" note — a prompt is a request, not a control), `app/projection_copy_guard.py` on BOTH live serve paths in `main.py` (the opportunities list and the executive report compose their responses from stored opps directly, not through `build_executive_report`, so a guard in the report engine alone misses them) — scrubbing returns COPIES, the stored opportunity is never rewritten, and `agentTopic` sanitising in `routes_sprint41_blueprint.py`. **Never write recommendation copy in a frontend component** — the guard only covers what the backend emits. `provenance.py` (T6) is the STORED projection's identifying stamp (runId/oppId/opportunityIdentity/createdAt/org/pack/schema versions), applied at STORE time by `app/projection_store.py` and NOT inside `build_projection` — a clock read in the computed payload would break AC5 reproducibility. **2.0-A2 must compare `projection_core(...)` values, never whole payloads** (provenance differs by design on every recomputation; `projection_store.projection_matches_stored` implements the rule). See `docs/projection_recommendation_vocabulary.md` and `docs/projection_storage.md`.

* `backend/discovery/packs/versions/`: 2.0-C1 T3 (AT-828) pack **version archive** — the config artifact of each PRIOR pack version that remains runnable (`<pack_id>_pack_config.v<version>.json`), plus a README documenting the discipline. * `backend/discovery/packs/pack_version_context.py`: 2.0-C1 T3 the per-run **effective pack config** seam. A rolled-back pack must genuinely BEHAVE as its pinned version, not just carry its stamp. Detector lists are resolved eagerly by the runner, but the external config (thresholds/calibration/terminology) is read LAZILY deep inside detectors/scorers that call `get_detector_thresholds(section, fallback)` with no path argument — threading a path through every signature would touch dozens of call sites. So the runner publishes `{pack_id: archived_config_path}` here and BOTH pack config loaders apply one shared precedence via `resolve_config_path()`: **explicit path argument → this run's pinned path → the pack's default path**. A `contextvars.ContextVar` (not a module global) for exactly the reason `discovery/ingest/__init__.py`'s live-connector context is one: runs execute concurrently in background threads under `copy_context().run(...)`, and a global would leak one tenant's rolled-back config into another tenant's run. The accessor is `get_pinned_config_path()` — deliberately NOT `get_pack_config_path()`, which already belongs to `pack_config` and returns the pack's DEFAULT path; two same-named accessors returning different paths would be a footgun. `pack_config_paths(...)` is a context manager that restores the previous mapping on exit.
* `backend/app/history_retention.py`: 2.0-C1 T4 (AT-829) **run history is never deleted** — the single declaration of which tables hold run history (`PROTECTED_TABLE_REASONS`: `runs`, `run_events`, `kv`, `opportunity_instances`, `pack_state_history`, plus 2.0-C2 T2's `pack_certification_reviews` certification review trail) and the tables that are legitimately deletable with their justification (`DELETABLE_TABLE_REASONS`: `retrieval_chunks`/`retrieval_refresh_queue` — a DERIVED vector index + its work queue that R18-B2 freshness must be able to purge; `entity_relationships` — cross-run graph state `relationship_mapper` prunes). Three enforcement layers read this ONE set: (1) **DB privileges** — `provision.sql` + alembic `0033` `REVOKE DELETE, TRUNCATE` on every protected table AFTER the `GRANT ALL PRIVILEGES` block (ordering is load-bearing and pinned by a test); (2) a **build-breaking static sweep** (`tests/unit/test_never_delete_history.py`) that walks the tree at test time and fails CI on a delete against a protected — or an UNCLASSIFIED — table; (3) the runtime guard `guard_delete()`/`assert_no_history_deletion()`, which `db.delete_run_events` self-checks through. **Note for future work:** `db.py` previously claimed "the app DB role has UPDATE but not DELETE" — that was NOT true of this provisioning path (`GRANT ALL PRIVILEGES` includes DELETE), so the soft-delete shape of `delete_run_events` is now an ENFORCED contract rather than an assumption. `find_delete_targets()` excludes real SQL keywords (`ON`/`TABLE`/`CASCADE`/…) so a privilege statement like `REVOKE DELETE, TRUNCATE ON TABLE "kv"` does not parse `ON` as a target.
* `backend/app/pack_state.py`: 2.0-C1 T2 (AT-827) pack lifecycle state — the safe-disable state machine. Two states (`active`/`disabled`) and two transitions per `(org, pack)`; **absence of a row means `active`**, so provisioning changes no behaviour until a customer disables something (no seed, no backfill). Both transitions are idempotent (a repeat returns `changed=False` and writes no history row). Storage is `pack_states` + `pack_state_history` (alembic `0031`, mirrored into `provision.sql`, DDL in `database/models/pack_states.py`) behind the same abstract-store + `InMemory`/`Postgres` + `_STORE` singleton + `set_pack_state_store()` injection seam as `runbook_match_decisions.py`. Pack-id validation is deliberately STRICTER than `get_pack()` — an unknown id raises `PackNotFound` rather than resolving to the default pack, because silently disabling `service_cloud` on a typo would be a foot-gun. **There is no delete path in this module** — re-enabling writes a NEW state and a NEW history row rather than removing the disable, which is what makes the history an audit trail (2.0-C1 AC4; tests pin that the module contains no `DELETE`/`DROP`/`TRUNCATE` and that the store contract exposes no delete/remove method). **Reads are fail-soft** (`disabled_pack_ids_safe`): an unreadable store — including a deployment that has not yet applied `0031` — reads every pack as active, because "historical findings remain retrievable and viewable" outranks the label, so the LABEL degrades before the finding does. **Writes are NOT fail-soft** — a disable that did not persist must never look like it succeeded. **2.0-C1 T3 (AT-828)** adds the SECOND, independent lifecycle dimension to the same module and row: a **version pin** (`rollback_pack_version`/`restore_pack_version`/`set_pinned_pack_version`, `pinned_version` column via alembic `0032`). State and version never overwrite each other — disabling a rolled-back pack keeps its pin, re-enabling does not lose it — but they share one `revision` counter and ONE append-only history trail (transitions `rollback`/`restore` alongside `disable`/`enable`), because AT-830 has to surface "what has this org done to this pack" and one trail means one answer. A rollback target must have an ARCHIVED artifact or `PackVersionUnavailable` is raised naming what is available; pinning to the pack's CURRENT version normalises to no pin (storing it would leave a stale pin silently holding the pack back after the next bump). `pinned_pack_versions_safe` degrades to "no pins" — note the direction: the run then executes AND is stamped with the current version, so it stays self-consistent and merely fails to honour the rollback, which is the safe failure for AC3.
* `backend/app/routes_pack_state.py`: 2.0-C1 T2 pack-state API, **registered** in `main.py` via `register_pack_state_routes(app)`. `GET /api/packs/state` (viewer+ — a viewer who sees a "now-disabled pack" label must be able to confirm it), `PUT /api/packs/{pack_id}/state` (**owner** — turning off a pack alters what every future run for the whole org produces, the same bar as connector connect/disconnect; body is the TARGET state so the call is idempotent), `GET /api/packs/{pack_id}/state/history` (analyst+, newest-first per the repo audit convention), and **2.0-C1 T3** `PUT /api/packs/{pack_id}/version` (**owner** — `{"version": "1.1.0"}` rolls back, `{"version": null}` restores the current version; **409** naming the available versions when the target is not archived). Org-scoped via `get_current_org_id()` only — a request body never carries an org id. A real transition emits the `pack_state_changed` audit event and `pack.state_changed` telemetry; a no-op transition emits neither. `GET /api/packs/state` reports `pinnedVersion`, `effectiveVersion` (what a run started NOW would execute and stamp — the number an operator actually cares about, vs `packVersion` which stays what the registry ships), and `availableVersions`. **2.0-C1 T4 (AT-829)** makes a REMOVED pack's retained history reachable: `pack_state_view` includes ORPHANED rows (state for a pack no longer in `PACK_REGISTRY`) flagged `registered: false` with `null` version fields, and the history endpoint is gated on `has_pack_lifecycle_record()` rather than registry membership. * `backend/app/pack_certification_review.py`: 2.0-C2 T2 (AT-832) the certification review workflow — discharges "every certification decision is recorded with reviewer, criteria, and date, and is auditable" (2.0-C2 AC5). A review RECORDS a human decision; it never grants a badge — only the AT-831 signature does, and if a database row could change a level then the reviewer's row would be the trust root instead of the signing key, which is the exact self-application hole the signature closes. `PackCertificationReview.approved_declaration()`/`canonical_payload()` are the bridge: they emit the exact declaration and exact bytes for the key holder to sign OFFLINE, so what is signed is provably what was approved (a rejected review raises instead, and its serialised form omits both signing fields). Approval is GATED on the checklist — every required criterion must carry a PASSING verdict, with missing and failed reported separately because they are different mistakes; `not_applicable` is allowed but must carry a note and never satisfies a required criterion; a rejection must carry notes. Attribution is server-side (reviewer from the token, pack/platform version and date from the server) — a trail the caller can back-date is not an audit trail — and the pack id is validated strictly (`PackNotFound`) rather than resolved to the default pack, so a typo cannot put a real reviewer's name against a pack they never saw. Same abstract-store + `InMemory`/`Postgres` + `_STORE` singleton + `set_review_store()` injection seam as `pack_state.py`. **There is no update and no delete path** — re-reviewing appends the next revision — and `pack_certification_reviews` is in `history_retention.PROTECTED_TABLES`, so migration 0045 REVOKEs DELETE/TRUNCATE on it. Reads are fail-soft (`latest_reviews_safe`), writes never are.
* `backend/app/pack_certification_policy.py`: 2.0-C2 T4 (AT-834) the per-org certification ACTIVATION POLICY — discharges "an org policy restricting to Certified prevents activation of Partner/Community packs, with a clear reason" (2.0-C2 AC3). The policy is a FLOOR (minimum level), not a permitted-level list, because the levels are ordered — an org accepting Partner necessarily accepts Certified, and a set would allow the meaningless "community but not partner". `community` is the default floor and restricts nothing, so provisioning changes no behaviour until an org opts in (the `pack_state` discipline). A violation REFUSES (409) rather than excluding, unlike a disabled pack: quietly dropping the pack would leave a federal reviewer unable to tell a policy block from a pack that found nothing. The refusal names every offending pack, the level it holds, and — when the pack CLAIMED more than it can prove — that the claim could not be verified. **Reads FAIL CLOSED, deliberately unlike every other pack-lifecycle read**: an unreadable policy (`PackCertificationPolicyUnavailable` → 503) or an unverifiable pack level under an active restriction refuses activation rather than assuming compliance — a security control that fails open would lift the restriction exactly when it matters. With no restriction set the check short-circuits before any signature is verified, so a deployment that has not opted in pays nothing. Enforced inside `pack_activation.resolve_activatable_packs` (stage 3 of 4, after compatibility so the more fundamental reason is reported first), which is the ONE resolution both API edges and `discovery/runner.py` call — a CLI caller cannot walk around it. Disabled is evaluated FIRST on purpose — a pack the customer already turned off must not be able to fail a run on compatibility grounds, since it is not going to execute either way. **2.0-C1 T3 adds a third stage** after those two: apply this org's VERSION PINS, so a rolled-back pack contributes its pinned version plus that version's archived config path (`ActivationDecision.pinned_versions` / `.pinned_config_paths` / `.effective_version()`). The two refusal rules differ in a principled way: **incompatible** = "this pack CANNOT work here" (a configuration error → 409), **disabled** = "this pack is intentionally turned off" (a deliberate ongoing state → excluded, run proceeds with the rest). * `backend/discovery/packs/sdk/`: 2.0-C3 Skills SDK — the partner pack authoring surface, dependency-free of `app` (offline tooling reads it). `manifest.py` (T1 / AT-836) is the **pack manifest schema**: the declarative document defining pack identity, the 2.0-C1 `compatibility` block, a certification PLACEHOLDER, detectors composed from primitives with parameters, scorer calibration, terminology, and template defaults — plus `validate_manifest` (never raises; reports EVERY error with a JSON path + machine-readable code), `parse_manifest`/`load_manifest`, `manifest_fingerprint` (SHA-256 over canonical JSON, reusing `pack_certification.canonical_payload_bytes`, so packaging can bind a bundle signature to exactly this manifest), `manifest_to_pack_config` (projection into the `PACK_REGISTRY` shape so an authored pack rides the EXISTING lifecycle — compatibility gate, disable, rollback, certification — rather than a parallel path), and `manifest_schema_reference()` (the authoring reference, generated from the same constants validation uses so docs cannot drift). The schema is **closed by design**, because 2.0-C3's governing constraint is that no partner-supplied executable code runs in a customer deployment: an unknown key anywhere is a hard error (a schema that ignores what it does not understand is one an author can smuggle through), detectors name a PRIMITIVE and there is no module-path field at all, every parameter is typed AND bounded (`max_depth` caps at 3 — an unbounded traversal shipped as "configuration" is still unbounded), every concept must be in `platform_capabilities.NORMALISED_CONCEPTS` AND declared in the manifest's own compatibility block (else the C1 gate would be a lie), and a document-wide code sweep refuses code-shaped keys (`module`/`script`/`eval`/`entrypoint`/…) and values (imports, lambdas, dunders, shebangs, executable file suffixes, dotted module paths in identifier fields) at any depth. The import pattern is anchored on the `import` keyword, not a bare `from`, so ordinary pack prose ("findings from ServiceNow queues") is not flagged — a sweep that cries wolf is one authors route around. * `backend/discovery/packs/pack_deprecation.py`: 2.0-C4 T1 (AT-842) pack deprecation metadata — "a pack version can be marked deprecated with a reason, a grace period, and an optional replacement pack". Declared under `pack_config.DEPRECATION_KEY`, deliberately NOT in per-org `pack_states` — that table is the CUSTOMER's dimension (disable, rollback), and merging the two would let a customer "undeprecate" a superseded pack or make a vendor notice look like a customer decision. * `backend/app/pack_migration.py`: 2.0-C4 T3 (AT-844) the org-config migration off a DEPRECATED pack — discharges "migration previews the config change, applies it on confirmation, and is reversible" (2.0-C4 AC2). * `backend/app/pack_grace.py`: 2.0-C4 T4 (AT-845) deprecation GRACE behaviour — discharges "the pack runs normally during grace and moves to safe-disabled after it, with history intact" (2.0-C4 AC3). Half of this module is a NEGATIVE: a pack inside its grace is activated, runs its detectors, and has NO state row written — there is no path here that can exclude, degrade, or re-version it, because a grace period that quietly changed behaviour would make the notice the change rather than a warning about one. Per R17-D3 Addendum A T13 (AC12), `backend/.env` / `.env.example` / `.env.template` contain **no per-client connector credentials** — only instance configuration; do not add credential env vars to them.

Section A (AT-515, unchanged) is the whole-backend, literal-env-var-name sweep. Inline secrets in a target config are rejected. These connectors are gated on `java_app` / `dotnet_app` being in the run's connected systems.
* Native AWS event ingestion (`aws_events`, MSP-B1) is configured, not discovered. The everyday path is the Integration Hub AWS card (Owner connects the hub key, then PINS each managed account); `discovery/ingest/aws_events_config.py` reads that back per org and is what puts `aws_events` into a live run's systems set (`live_ingest_credentials._resolve_aws_events`) and into `discovery/runner.py::_ingest_aws_events`, which runs it when a `cloud_ops` pack is selected and merges its records into the same cloud-ops assembly as the B8 bridge and the B2 Azure connector. * Native cloud-event poll bounds (MSP-B1, shared by the AWS and Azure native connectors): `CLOUD_EVENT_MAX_POLLS_PER_SCOPE` (default `4`) caps how many TOTAL polls one run performs per scope (account × region × surface) — the first poll counts, so `4` means four polls and `1` means poll once and never continue; `CLOUD_EVENT_POLL_DEADLINE_SECONDS` (default `180`) is the wall-clock budget for the whole poll phase, consulted for continuation polls only so no scope is starved of its first poll; `AWS_EVENT_MAX_BACKFILL_DAYS` (default `30`) bounds how DEEP an initial CloudTrail backfill walks, measured from the backfill's own newest event. `0` disables any of the three. Whatever a bound leaves unread resumes from the checkpoint on the next run, is logged at WARNING, and is named in the run's `cloudOpsRuntime.awsEvents.poll` health block (which reports `complete: false`) — a partial ingest is never reported as a clean one. Raise `AWS_EVENT_MAX_BACKFILL_DAYS` for a deeper first load, or lower the two poll bounds to shorten the ingest stage on a busy estate.

* Enterprise-app code/structure (R18-A6) app→repo mapping is configured, not auto-discovered: which A2-ingested repos ARE an application is declared per org in `ENTERPRISE_APP_REPOS` (offline reads `discovery/enterprise_apps/fixtures/enterprise_app_repos.json`). Each entry is secret-free (`app_id`/`name`/`platform`/`repos`/`metadata`); a mapping carrying an inline credential field is rejected (same shared guard as the operational app targets), and a repo belongs to exactly one application. `app_id` matches phase one's running-app identity so the runtime→structure join has a key. See `discovery/enterprise_apps/app_repo_map.py`.
* Cross-source entity alias mappings (2.0-B2 T1) are org-scoped state, not env config: the table lives in `kv` under `entity_alias_mappings:{org_id}` and is written only through `app/entity_alias_mappings.py::put_alias_mappings` (which validates and rejects a conflicting table). `ENTITY_ALIAS_MAPPINGS` overrides it for offline/dev or for a deployment that prefers to declare it as configuration — a JSON array, or an object keyed by org id with a `default`/`*` fallback (the `ENTERPRISE_APP_REPOS` shape). Non-secret. A malformed override raises at read time (an operator who set it deliberately must see the mistake); an invalid STORED table only disables tier-2 merging, with a warning.
* Document ingestion (`documents`, R18-A1) is configured, not discovered: offline (default) reads the deterministic `fixtures/documents_sample.json`; live scans the per-deployment `DOCUMENT_LOCATIONS` (a JSON array of `{"location", "path"}` directory configs) for direct on-disk/mounted document locations AND composes in the SharePoint/Confluence attachment sources (T5, `documents_attachments.py`) — a connector not connected simply contributes nothing (the composite isolates each source). No credentials are read for the configured-location scan; the SharePoint/Confluence sources reuse their connectors' vaulted OAuth tokens.
* Document ingestion (`documents`, R18-A1) is configured, not discovered: offline (default) reads the deterministic `fixtures/documents_sample.json`; live scans the per-deployment `DOCUMENT_LOCATIONS` (a JSON array of `{"location", "path"}` directory configs) for direct on-disk/mounted document locations. SharePoint/Confluence attachment surfacing is a separate source wired in a later task (T5). No credentials are read here for the configured-location scan.
* Document extraction caps (R18-A1 T4): `DOCUMENT_MAX_FILE_BYTES` (default 26214400 = 25 MiB; `0` disables) is the per-file size cap — a larger file is skipped-with-reason `size_capped` (never read when the source knows the size). `DOCUMENT_EXTRACTION_BUDGET_BYTES` (default 268435456 = 256 MiB; `0` disables) is the per-run extraction budget — once that many content bytes have been read in a run, remaining changed files are skipped-with-reason `budget_exceeded` and retried next run. A `size_capped` skip advances the checkpoint (deterministic); a `budget_exceeded` skip does not (transient). Both are overridable per `DocumentIngestor` via constructor args.
* OAuth client secrets (production, enforced by `REQUIRE_CONNECTOR_SECRETS`): `SALESFORCE_CLIENT_SECRET`, `SERVICENOW_CLIENT_SECRET`, `JIRA_CLIENT_SECRET`, `GITHUB_CLIENT_SECRET`, `SLACK_CLIENT_SECRET`, `TEAMS_CLIENT_SECRET`, `SAP_CLIENT_SECRET`, `DYNAMIC365_CLIENT_SECRET`. Teams (Microsoft Graph) also reads `TEAMS_TENANT_ID` (Entra tenant GUID, or `organizations`; default `organizations`) — see `app/auth/configs.py`.
* `CREDENTIAL_VAULT_KEY`: Fernet key for token vault encryption. Required in production; missing it causes connector secret storage to fail or fall back to plaintext.
* `DEV_JWT_ROLE`: role override for the dev token (`owner`/`analyst`/`viewer`). Used alongside `ADMIN_JWT`, `ANALYST_JWT`, `VIEWER_JWT` in contract tests.
* `INGEST_MODE`: `online`/`offline`/`test` — controls the ingestion path.
* `DEPLOYMENT_PROFILE` (HP-2 T1): **who runs this deployment** — `saas` (default) or `customer_hosted`. Read live via `app/deployment_profile.py` (`get_deployment_profile()` / `is_customer_hosted()` / `is_saas()`), which is the ONLY module permitted to read the var — a contract test (`tests/contract/test_deployment_profile.py`) walks the backend AST and fails the build on any other direct read, so HP-2.2/2.3/2.5 consume the helper rather than each re-deriving the comparison (the eight-hand-copied-guards shape HP-1 exists to fix). Unset/blank → `saas`, so no existing deployment changes behaviour; **any other value RAISES `InvalidDeploymentProfile`** — deliberately the opposite posture to `NETWORK_PROFILE` below, and the asymmetry is pinned by a test so nobody "harmonises" them. The safe direction differs: an unknown `NETWORK_PROFILE` degrades toward the FULL experience (worst case, a connect flow is offered and fails), whereas an unknown `DEPLOYMENT_PROFILE` degrading to `saas` would hand a customer-hosted deployment the cloud-calling default HP-2 exists to remove — so a typo like `on_prem` or `customer-hosted` fails loudly. The vocabulary is CLOSED (`on_prem` is deliberately not an alias); the helpers propagate the error rather than reporting `False`, since a misconfigured profile read as "not customer-hosted" is the same silent reinstatement. `validate_deployment_profile()` is called FIRST in `main.py`'s lifespan so a bad value refuses boot rather than 500ing whichever request first consults it. **Orthogonal to `is_production()`, which is unchanged** (`ENVIRONMENT=production` only): a customer-hosted STAGING box is `customer_hosted` and NOT production — its boundary is real, but it is not subject to production credential rules — and a SaaS production box is the mirror case, so deriving either from the other gets one of the two wrong. Structural tests pin that `is_production` reads neither the profile var nor the profile function, and that the module docstring records the distinction.
* `NETWORK_PROFILE` (R18-A3 T5 / AT-558): deployment inbound-network posture — `standard` (default) or `no_public_inbound`. Read live via `app/network_profile.py` (`get_network_profile()` / `is_no_public_inbound()`); unset/unrecognised falls back to `standard`. In `no_public_inbound` the Integration Hub hides the authorization-code Connect button for any connector with an outbound-only mode and shows the outbound setup path instead (AC4). Exposed with a per-connector auth-capability map at `GET /api/network-profile` (viewer+, in `routes_connector_auth.py`), built from `auth_modes.get_connector_auth_capability()`. The flag lives at the connect/setup edge only — ingestion stays mode-agnostic.
* Model provider gateway (R16-D1 / R17-D1 / R17-D2): `MODEL_GENERATION_PROVIDER` and `MODEL_EMBEDDING_PROVIDER` select which provider serves generation and embedding **independently** (valid values: `hosted` (default), `in_boundary`, `customer_tenant`). Resolved at call time; unknown values raise at startup via `validate_provider_config()`. All three modes register through `register_provider()` in `model_gateway/__init__.py`; adding a provider requires no calling-code change. **HP-2 T2 made the DEFAULT conditional on `DEPLOYMENT_PROFILE`**: `hosted` is the default under `saas` only — under `customer_hosted` there is NO default and an unset (or blank) variable raises `MissingProviderConfiguration`, naming BOTH variables and every valid value. The point is that a call leaving the customer's boundary must be a configured choice, never an inherited one; setting `hosted` deliberately is still permitted (HP-3 audits the transmission). SaaS resolution is byte-identical to before, *including* the pre-existing behaviour that a present-but-BLANK variable falls through to `_resolve_provider` and fails as an unregistered name rather than becoming `hosted` — widening blank to mean "unset" would silently turn a typo into a cloud call, and a regression test pins it. `_configured_provider_name()` is the SINGLE place the fallback is decided (before T2 the same `os.getenv(var, _DEFAULT_PROVIDER)` line sat in four places — the shape HP-1's eight copied org guards warn about); an AST test fails the build on any inline `_DEFAULT_PROVIDER` fallback. The refusal fires from `validate_provider_config()` — already called unconditionally by the lifespan — so a config error stops the process rather than surfacing on whichever request first needs a model; the getters share the same helper (so a CLI/worker that skipped startup still fails loudly instead of calling out) but carry no second copy of the rule. `resolve_provider_names()` keeps its non-raising contract and now returns `Optional[str]`, reporting `None` rather than `hosted` when nothing is configured — naming a provider the deployment never used would corrupt 2.0-D4 T3's reproducibility record.
* `MODEL_PROVIDER_PROBE_TIMEOUT_SECONDS` (HP-2 T3, default `3`; `0` disables): the **startup posture probe** in `app/model_gateway/probe.py`. HP-2.2 stopped a customer-hosted deployment *inheriting* a cloud provider; T3 checks whether the provider that WAS configured actually works. Three checks per role, cheapest-first, **first failure reported**: `endpoint_configuration` → `credential_presence` → `reachability`. Reachability is ONE bounded TCP connect to the endpoint host/port — never a model call (a model call costs money, needs a valid credential, and could not distinguish "unreachable" from "wrong key", which the ACs require to be distinct) — and **no retries**, since a retrying probe reproduces the startup hang this exists to make loud. Credential presence is checked BEFORE reachability because a connect succeeds for a provider with no key and would report `ok` while every call is about to 401; `in_boundary` declares `credential_required=False` because Ollama/vLLM are commonly unauthenticated, so failing startup there would break the exact on-prem customer HP-2 serves. **Severity is profile-dependent**: under `customer_hosted` an unhealthy role raises `ProviderUnreachable` and refuses boot (no fallback exists); under `saas` it is logged and recorded as unhealthy posture but never blocks startup (a transient hosted-API blip must not stop the service). `unknown` NEVER blocks boot — it means the posture was not established, and refusing to boot over an unmeasured provider turns "we did not look" into "it is broken". Statuses come from `app/degradation.py`'s canonical set (a structural test fails the build if `probe.py` restates any `STATUS_*` literal); `unreachable` and `not_probed` were added to `NATIVE_STATUS_MAP`, which is the documented way to extend that vocabulary. The per-provider target comes from `ModelProvider.probe_target(role)` — a default-implemented interface method following the `embedding_identity()` precedent, so adding a provider needs no probe-module edit — and `ProviderProbeTarget` structurally **cannot carry a credential value** (only `credential_required`/`credential_present` plus the config key NAME; a test pins its field set and greps `probe.py` for `resolve_api_key`/`api_key`). Wired into `validate_provider_config()` rather than a parallel validator, with the try/except scoped to EVALUATION only so a probing bug cannot block startup while a deliberate refusal is not swallowed (a test asserts the ordering). The posture is evaluated once and cached (`model_gateway.provider_posture()`, the read HP-2.5 consumes) — reading it never re-probes, so a health endpoint cannot become a DoS lever pointed at the customer's own model server. Probing is also skipped when `AGENTIQ_DISABLE_BACKGROUND_JOBS=1`, which the contract conftest already sets, so no test reaches the network.
* **Health reflects model posture (HP-2 T5)** — `app/model_provider_health.py` shapes HP-2.3's cached posture into `GET /api/health`'s `checks.model_providers` (roles → `{provider, status, check, probed}`), and an unreachable provider drives `status: unhealthy`. Before T5 the endpoint reported `healthy` on database connectivity alone, so a deployment whose model was unreachable looked fine while findings lost their AI narrative and retrieval evidence. Legacy `{ok, ts}` and the `database` check are unchanged (a regression test pins them); `/health` — the dumb liveness probe — is untouched. **Two constraints come from the route being PUBLIC** (`/api/health` is in `test_rbac_enforcement._PUBLIC_ROUTES`, no credential required): it reports **no endpoint host** (an in-boundary model host is internal topology; the full detail stays in T3's startup WARNING) and it **never re-probes** (a public endpoint opening sockets per request would be a lever against the customer's own model server — structural tests pin both). **Only a `reachability` failure degrades the top-level verdict**, via `role_degrades_health(status, check)`; `degrades_overall_health()` takes the shaped payload rather than a bare status because the rolled-up status alone cannot say what caused it. The exclusions are reasoned, not lazy: `unknown` means nobody looked (the same rule T3 uses to decide whether to refuse boot); a missing credential or unconfigured endpoint already refuses boot under `customer_hosted`, and under `saas` is a SUPPORTED configuration because LLM enrichment is optional by design — the deterministic fallbacks work with no `ANTHROPIC_API_KEY`, and the shipped dev/test setup has none, so degrading on it would make every dev box and every contract run report unhealthy. The check's own status stays honest in all of those cases — not degrading is not the same as hidden.
* **Embedding-dimension consistency (HP-2 T4)** — `app/retrieval/dimension_guard.py` + `app/retrieval/embedding_dimensions.py`, called from `main.py`'s lifespan AFTER `validate_provider_config()` (the active model must resolve before its dimension means anything). No env var: it runs automatically and needs no configuration. **The dimensionless `vector` column is NOT changed** — `database/models/retrieval.py` declares it unqualified on purpose (model portability; a test asserts it stays that way), and this only adds the check the flexible column cannot do itself: that the CONFIGURED model emits the dimension already stored under the active `(embedding_model, embedding_model_version)` stamp, which previously surfaced as a storage error on the first write. **Only the ACTIVE stamp is examined** — vectors under another stamp are never compared against it (`store.search` filters on the pair), so they may legitimately differ; they are the R18-B2 T5 backfill's work. That fact changes the REMEDY, and the message says so: **the backfill does not fix this**, because it only re-embeds vectors stamped by a NON-active model and these already carry the active one — so the message names repinning the model, or moving the model VERSION so the rows become non-active and the backfill can reach them. Declared dimensions live in `embedding_dimensions.py` (`MODEL_DIMENSIONS`, each entry carrying a `basis` of `published`/`measured`, the `ops_calibration.py` convention); a model ABSENT from it has no declaration so the check is SKIPPED, never failed — an unknown model is not a mismatch, and adding one is a one-line change with no migration and no re-embed. Measuring a real dimension would require an embedding call (billable, needs a credential and reachability), which is why a table exists at all; Ollama tags are folded (`nomic-embed-text:latest` is the same vector space). **Skipped is reported distinctly from ok** — first run with nothing embedded, unknown model, unresolvable provider, and unreadable store all skip (the last with a warning that says it is *not* evidence the dimensions agree). Unlike HP-2.3's probe the refusal is **profile-independent** (a structural test asserts the guard never reads `DEPLOYMENT_PROFILE`): this is not environmental, the model provably cannot write into the index whoever operates the deployment. `store.stored_embedding_dimensions()` is the read — pgvector `vector_dims()`, grouped, returning dimensions/chunk-count/org-count only and never content; it spans orgs because a conflict inside one stamp is a store-wide fact, and a build without `vector_dims` raises and is treated as "cannot determine".
* In-boundary provider config (R17-D1, used only when a provider above is set to `in_boundary`; all owned inside `backend/app/model_gateway/` — no caller reads these): `IN_BOUNDARY_BASE_URL` (common OpenAI-compatible base; the adapter derives `/v1/chat/completions` and `/v1/embeddings`), `IN_BOUNDARY_GENERATION_ENDPOINT` / `IN_BOUNDARY_EMBEDDING_ENDPOINT` (override either path independently), `IN_BOUNDARY_API_KEY` (bearer token, resolved live per call — never logged), and the model names `IN_BOUNDARY_MODEL` (common fallback) / `IN_BOUNDARY_GENERATION_MODEL` / `IN_BOUNDARY_EMBEDDING_MODEL`. Leave all blank unless in-boundary mode is in use. If `in_boundary` is selected with no endpoint URL configured, `validate_provider_config()` logs a startup warning (calls never raise — they degrade to `ok=False`/`[]`).
* **On-prem `in_boundary` configuration is documented, not improvised (HP-2 T7).** The two validated templates are `deployment/ON_PREM_OLLAMA.md` and `deployment/ON_PREM_VLLM.md`; `backend/.env.template` points at them rather than restating the recipe. Three things they settle that are easy to get wrong from the variable names alone: the per-role endpoint overrides are **complete URLs including the path** and are never joined to `IN_BOUNDARY_BASE_URL` (that is what makes generation and embeddings on different hosts work); `IN_BOUNDARY_API_KEY` is **optional** and there is exactly **one** for both roles, so two servers requiring different keys need a normalising proxy; and the retrieval worker sends up to `RETRIEVAL_EMBED_BATCH_SIZE` texts (default 64) per embedding request, so a server that cannot batch indexes NOTHING unless that variable is lowered to 1. Under `DEPLOYMENT_PROFILE=customer_hosted` a model server that starts AFTER the app fails the HP-2.3 reachability probe and refuses boot — order the service units, or set `MODEL_PROVIDER_PROBE_TIMEOUT_SECONDS=0` and accept losing the check.
* Customer-tenant provider config (R17-D2, used only when a provider above is set to `customer_tenant`; owned inside `backend/app/model_gateway/customer_tenant_config.py` — no caller reads these): targets the customer's **managed** in-tenant model service (e.g. Azure OpenAI). `CUSTOMER_TENANT_ENDPOINT` (resource base; the adapter builds `{endpoint}/openai/deployments/{deployment}/chat/completions|embeddings?api-version=...`), `CUSTOMER_TENANT_API_VERSION` (defaults to a GA version), `CUSTOMER_TENANT_DEPLOYMENT` (common fallback) / `CUSTOMER_TENANT_GENERATION_DEPLOYMENT` / `CUSTOMER_TENANT_EMBEDDING_DEPLOYMENT`, `CUSTOMER_TENANT_GENERATION_ENDPOINT` / `CUSTOMER_TENANT_EMBEDDING_ENDPOINT` (verbatim full-URL overrides for non-Azure-path managed endpoints), `CUSTOMER_TENANT_EMBEDDING_MODEL` / `CUSTOMER_TENANT_EMBEDDING_MODEL_VERSION` (the UNDERLYING model behind the embedding deployment alias and its model version — see the R18-B1 note below), and `CUSTOMER_TENANT_API_KEY` (tenant credential sent via the `api-key` header, resolved live per call — never logged). Same resilience/graceful-failure posture and self-emitted `provider='customer_tenant'` telemetry as the other two modes. Leave all blank unless customer-tenant mode is in use.
* **Retrieval embedding provider (R18-B1).** The retrieval substrate is INERT without an embedding provider: the default `hosted` (Anthropic) provider has no embeddings endpoint, so `MODEL_EMBEDDING_PROVIDER=hosted` leaves every `retrieval_chunks` row pending forever and every search returning nothing — silently. `validate_provider_config()` logs a startup WARNING for exactly this. The shipped configuration serves embeddings from Azure OpenAI via `customer_tenant` (`MODEL_EMBEDDING_PROVIDER=customer_tenant`, deployment `AgentIQ-text-embedding-3-small`, model `text-embedding-3-small` v1, api-version `2024-12-01-preview`, 1536-dim vectors) while generation stays `hosted` — the two resolve independently. The full recipe is in `backend/.env.template`; only `CUSTOMER_TENANT_API_KEY` is secret. **`CUSTOMER_TENANT_EMBEDDING_MODEL` / `_MODEL_VERSION` are what the AC8 per-vector stamp names**, in preference to the deployment alias + api-version fallback: a deployment name is an operator-chosen alias and the service api-version versions the REST surface, not the model, so keying the stamp on either would invalidate the whole index and force a full re-embed of unchanged content on a routine api-version bump or a deployment rename. Stamping the model means the identity moves only when the vector space genuinely changes. `backend/scripts/verify_retrieval_substrate.py` is the live end-to-end check (ingest → chunk → embed → index → retrieve, with the AC3/AC4/AC5/AC7/AC8 assertions).
* Customer-tenant credential vault (R17-D2 T2): the tenant credential is Fernet-encrypted at rest in the shared `credentials` table (reused — no schema change) under the reserved `connector_id = "customer_tenant"`, keyed per org, exactly like connector OAuth tokens. `app/auth/vault.py` owns `store_customer_tenant_credential` / `get_customer_tenant_credential` / `revoke_customer_tenant_credential` (a static key — no OAuth refresh path). Only the gateway resolves it: `app/model_gateway/customer_tenant_vault.py` `resolve_customer_tenant_api_key()` reads the vault first (org from the tenancy context, default org otherwise), then falls back to the `CUSTOMER_TENANT_API_KEY` env var for dev/standalone. The read path never raises and never logs the value; a missing/revoked/undecryptable credential resolves to `""`, and the provider short-circuits to a graceful failure (`ok=False` / `[]`) with no network call. In production the credential lives only in the vault, so a customer revoke fully cuts access. **R1.9.1-H1 T4 (F4 fix):** the env fallback is now gated on `app/deployment_profile.py`'s `is_production()` — the single source of truth for "is this process production" (`ENVIRONMENT=production` OR `REQUIRE_CONNECTOR_SECRETS=1`; `app/main.py`'s `_is_production()` delegates to the same function, so the two checks cannot drift) — rather than checking `REQUIRE_CONNECTOR_SECRETS` alone, so `ENVIRONMENT=production` now also suppresses the fallback. The paired `validate_no_production_env_fallback()` is wired into `model_gateway.validate_provider_config()` (called unconditionally at startup regardless of which provider is selected) and logs a WARNING naming `CUSTOMER_TENANT_API_KEY` — never its value — when the var is set under production; it is pure operator-visibility since the var is already provably unread in that case. `CustomerTenantConfig.resolve_api_key()` is the only other path into this credential and delegates entirely to `resolve_customer_tenant_api_key()`, so the guard cannot be bypassed.
* `PACK_SANDBOX_MAX_CASES` / `_MAX_RECORDS_PER_CASE` / `_MAX_TOTAL_RECORDS` / `_MAX_FIXTURE_BYTES` / `_TIMEOUT_SECONDS` (2.0-C3 T6 / AT-841): the bounds an authored pack's fixtures are judged within, at install and before activation (defaults 50 / 2000 / 20000 / 4 MiB / 30s). Not a credential.

## Architecture Notes

* The API protects most endpoints with `require_auth`; tests usually pass `Authorization: Bearer dev-token-change-me`.
* PostgreSQL stores most tables as `{ id, payload }` JSON rows, plus `runs`, `run_events`, and run-scoped KV entries. `backend/app/db.py` handles this layer, serving every query from a process-wide connection pool (see the `db.py` entry above).
* `backend/database/connection.py` is a separate psycopg2 layer (telemetry connection/session helpers). Do not conflate with `db.py`; it does not share the `db.py` pool.
* Run lifecycle starts at `POST /api/runs/start`, then materialization writes status, events, opportunities, evidence, clusters, roadmap, executive report, and enrichment into run-scoped storage.
* Replay should re-serve persisted artifacts only. It must not call live ingestion or regenerate LLM output.
* LLM enrichment is advisory post-processing. It must not mutate scoring fields such as impact, effort, tier, decision, or evidence IDs.
* `OppEnrichment.relationships` is intentionally different from the other enrichment fields: it is read live from `entity_relationships` through `graph_query.py`, not from a run-scoped KV artifact. The graph is cross-run state, so later relationship upserts can change what a historical run's relationship view returns.
* `OppEnrichment` also carries ENT-2 cross-system corroboration fields (`corroboration_sources`, `corroboration_label`, `triple_corroboration`, `corroboration_rule_ids`), populated from the stored opportunity record. See `backend/app/corroboration_engine.py` and `backend/discovery/packs/corroboration_rules.py`.

The sweep is **proven to reject**, not merely asserted: adding an unaudited mutating route, removing an existing emission, deleting a gap declaration, and emitting an unregistered type each turn it red (verified by experiment). Current state: 56 state-changing keys — **37 audit, 5 declared exempt, 14 declared gaps, 0 undeclared**. **The completion pass closed every action D4 names by hand.** The largest hole was scope pin/unpin: all seven SaaS scope routes (Slack/Teams channels, Jira projects, Confluence spaces, SharePoint sites, GitHub repos, Salesforce products) persisted a data-access grant with NOTHING recorded, while the registry-level check passed because the cloud and native-DB scope paths already emitted `scope_declared` — proof that asserting a TYPE is registered is not the same as asserting the ACTION is audited, which is why `TestD4NamedActions::test_every_named_action_with_a_route_audits` now maps each named action to its ROUTES and fails if any does not audit. Also closed: connector **create** and **edit** (`POST /connect` toggled status and `POST /configure` changed what ServiceNow reads, both unrecorded — delete was already covered; the connect route emits two EXPLICIT `log_event` calls rather than one with a conditional event type, because the sweep resolves each call site's type statically and a type chosen by an expression is exactly what it cannot verify), **run start** via `POST /api/stack-builder/launch` (the path the product actually uses — `run_started` was emitted by the `routes_sprint4_t2` path only), and the **SecOps evidence disclosure**, whose module docstring already described itself as "audited" while emitting telemetry only (a refused disclosure audits too, with `outcome: failure` — a trail recording only successful reads cannot answer "who tried to reach evidence they were not entitled to?"). `tests/contract/test_d4_named_action_audit_records.py` drives these routes and reads the STORED row back, because "the route called `log_event`" and "a record exists with the required fields" are different claims. It also surfaced that **POST `/api/workspace/members` is registered twice** (`routes_workspace` audits, `main` does not), so which handler serves the request — and whether an audit row exists — depends on route order; recorded by `test_no_shadowed_route_hides_an_audit_gap` rather than silently fixed, since de-duplicating a route is a behavioural change.

## Testing Guidance

* For backend API work, prefer focused contract tests in `backend/tests/contract/`.
* **Startup behaviour needs a SUBPROCESS test, and reachability cannot be tested in-process at all (HP-2.8).** `tests/contract/conftest.py` sets `AGENTIQ_DISABLE_BACKGROUND_JOBS=1` at import so no test reaches the network, and HP-2.3 skips probing under that flag — so every posture in the suite is `unknown` or mocked, and any in-process assertion about an unreachable provider is vacuous. `tests/contract/test_hp2_startup_integration.py` is the pattern to copy: it boots the REAL app through its REAL lifespan in a subprocess with a per-scenario environment and the flag removed, reporting a JSON verdict so a refusal is distinguishable from a crash. A subprocess is load-bearing rather than incidental — that flag is process-global and read at import, and the app package loads `.env` on import, so an in-process attempt either inherits the suite's probe-disabling flag or lets a real deployment value stand in for one under test. Keep such tests hermetic: `127.0.0.1:1` for unreachable, a local listening socket for reachable (the probe does a bare TCP connect and nothing more, so a plain listener is a faithful model server), and `MODEL_PROVIDER_PROBE_TIMEOUT_SECONDS=0` wherever reachability is not the behaviour under test — a verdict that depends on reaching a vendor API fails for reasons unrelated to the code. Note two behaviours that surprise people: with the probe off the CHEAPER checks still run, so `hosted` with no `ANTHROPIC_API_KEY` reports `unavailable` on `credential_presence` (not `unknown`) while health stays `healthy`; and when a boot's outcome depends on DATABASE state rather than environment, the boot cache must be keyed on that state too, or two scenarios with identical configuration serve each other's verdict and both pass regardless of the code.
* **Assert a guard by watching it fail.** Every HP-2 refusal is pinned by a negative control that removes the behaviour and confirms the tests go red — disabling the profile gate turns 8 red, neutering the startup dimension refusal turns 5 red (leaving the non-vacuity check correctly green), and making health never degrade turns exactly 1 red. A guard never observed failing is not known to be a guard.
* For discovery logic, test detectors/scorers/ingest in `backend/discovery/tests/` or the relevant `backend/tests/unit/` file.
* Contract tests seed an isolated, disposable PostgreSQL test database through `backend/tests/contract/conftest.py` (which installs its own connection pool and patches `db.connect`); do not make tests depend on a local dev database.
* For frontend API/state changes, mock API boundaries rather than reaching into backend files.
* For changes affecting the full run pipeline, verify start/status/artifact endpoints together.
* For native DB connector changes, run `backend/connectors/db/tests/` including the smoke tests for each driver.
* The CI gate (`.github/workflows/contract-tests.yml`) must pass on all PRs. Run `python -m pytest` locally before pushing.

## Known Gotchas

* **A model name with no declared dimension makes HP-2.4's startup check SKIP, not fail.** The dimension lookup folds a namespace prefix and a `:tag` suffix but nothing else, so `nomic-embed-text:latest` and `BAAI/bge-large-en-v1.5` resolve while Ollama's short tags `all-minilm` / `bge-large` and the versioned ids `nomic-ai/nomic-embed-text-v1.5` / `mixedbread-ai/mxbai-embed-large-v1` do not. Nothing breaks — but the check that exists to catch a dimension conflict at boot quietly does nothing. Serve the model under a declared name (`ollama cp`, or vLLM `--served-model-name`) or add the one-line row. Both HP-2.7 templates tabulate which names resolve.
* **Renaming a served embedding model triggers a re-embed of unchanged content.** The retrieval vector stamp is derived from `IN_BOUNDARY_EMBEDDING_MODEL` (`in_boundary:<model>`), so changing vLLM's `--served-model-name` — or aliasing a model to a new name — makes every existing vector non-active and the R18-B2 backfill converges the whole index. Harmless but not free; pick the served name once and keep it stable.
* **`AGENTIQ_DISABLE_BACKGROUND_JOBS=1` also disables the HP-2.3 provider probe**, so every posture reads `unknown` and anything downstream of it goes quiet: `/api/health` reports the check as `unknown` (never unhealthy), HP-2.6 stamps no `modelProviders` field on a run, and the `customer_hosted` startup refusal cannot fire. That is deliberate — the contract conftest sets it so no test reaches the network — but it makes any *verification* of reachability behaviour vacuous unless the variable is cleared first.
* `routes_sprint4_t5.py` exists in `backend/app/` but is **not registered** in `main.py`. Routes defined in it are silently inactive — always verify `main.py` registrations before assuming an endpoint exists.
* `PATCH_materialize_t2_t6.py` is a patch/migration file in `backend/app/`, not a regular module. Do not import it as a route or service.
* `routes_stack_builder.py` and `routes_stack_builder_launch.py` both exist with different responsibilities. Check `main.py` before editing either.
* `materialize_t3_hook.py` is a separate T3 materialization step, not an extension of `materialize_t2.py`. Do not merge them.
* `run_store.py` and `db.py` both deal with runs but have different scopes: `run_store.py` handles start/read of run records; `db.py` handles broader KV and table access. Do not consolidate without checking all callers.
* `backend/database/connection.py` (psycopg2 telemetry helpers) and `backend/app/db.py` (pooled psycopg2 access) are different layers with independent connections. Mixing them will cause session/connection conflicts.
* Two migration directories (`alembic/` and `migrations/`) serve overlapping purposes. Use `migrations/` for all new work — `alembic.ini` already points there.
* The CORS middleware allows any `localhost` port via regex in addition to the explicit origins list. This is intentional for dev flexibility.
* `backend/connectors/db/query_guard.py` must be invoked for every native DB query. Skipping it bypasses SQL injection protection silently.
* `auth/vault.py` requires `CREDENTIAL_VAULT_KEY` to be set in production. A missing key causes connector secret storage to fail or silently fall back to plaintext.
* `get_pack()` falls back to `service_cloud` for an unknown pack_id (it logs a WARNING rather than raising). A typo'd pack id therefore yields Service Cloud detectors instead of an error — check the log line if a run produces unexpected detectors.
* **There are now THREE distinct "decision" concepts on an opportunity, and they are not interchangeable.** (1) the run-scoped review `decision` (`APPROVED`/`REJECTED`/`UNREVIEWED`, in the `opps` KV blob) answers "is this finding real?"; (2) the 2.0-A2 T1 `opportunity_lifecycle` state answers "has the customer acted, and are we watching?"; (3) the 2.0-A3 T1 `opportunity_feedback` record answers "is this finding type worth our team's time?" and is the only one the learning layer reads. Only (2) and (3) are keyed on the stable `opportunity_identity` and survive a run; (1) is rewritten by materialization and reset by replay. Never collapse any two of them.
* `record_event()` raises `ValueError` for an unregistered `event_type` — this is a deliberate change from the earlier silent-drop behavior. A new event type must be added to `REGISTERED_EVENT_TYPES` before it is emitted, or the call raises.
* `ensure_entities_table()` is startup-only — it creates the entities table once when `routes_entities` is registered. Do not call it per-request.
* **ServiceNow `sysparm_display_value=all` returns every field as `{value, display_value}` — the two are not interchangeable.** `discovery/ingest/servicenow.py` has two accessors and picking the wrong one is a live-only bug (offline fixtures store plain scalars, so tests pass either way): `_optional_sn_text` prefers the human DISPLAY value (correct for names, groups, states, operational status) and `_optional_sn_raw_text` returns the RAW value (required for `sys_class_name` — raw `cmdb_ci_netgear` vs display "Network Gear" — and for EVERY datetime field, whose raw value is canonical `YYYY-MM-DD HH:MM:SS` UTC while the display value is rendered in the instance's date format and the user's timezone). Checkpoint cursors, delta windows, and time-to-resolve math all depend on the raw form.
* **A missing ServiceNow table is `unavailable`, not an error.** The MSP-B11 SecOps tables (`sn_si_incident`, `sn_vul_*`) exist only where the Security Incident Response / Vulnerability Response plugins are activated, and are readable only by a role the integration user may lack. `ServiceNowClient.table_available()` pre-flights each one (memoized per client) and the stream degrades to `status='unavailable'` with a named reason, no `error`, and no checkpoint movement — so it resumes cleanly if the module is later activated. `discovery/runner.py` reports these on `sn_data["servicenow_unavailable_tables"]` and does NOT flip the ServiceNow stage to partial for them. Transport failures still translate to `ServiceNowIngestError`; keep the request URL out of the message (it embeds the whole encoded query and is rendered verbatim in run health).
